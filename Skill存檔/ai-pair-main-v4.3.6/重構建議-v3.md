# AI-Pair 重構建議 v3

**討論日期：** 2026-04-28
**最後更新：** 2026-04-29
**現行版本：** SKILL.md v2.3.1
**目標版本：** v3.0

---

## 重構動機

現行架構有五個核心問題：

1. **缺少第三個異質 Reviewer** — 目前只有 GPT-4.1（bug/安全）和 Claude（架構），缺乏「需求對齊 + 遺漏偵測」的視角
2. **Agent 間通訊格式為人類可讀** — 所有中間報告都用 markdown 撰寫，造成大量無效 token 消耗
3. **沒有分層策略** — 簡單改動和複雜架構變更走一樣的 review 流程，成本不成比例
4. **Task context file 過大** — 多個任務合批在單一大文件（實測 408 行 / 16KB），dispatch 時整份文件被 agent 讀入
5. **Reviewer 重複讀相同檔案** — 多個 reviewer agent 各自獨立 Read 同一批 changed files，完整 source 被讀取 N 次

> **計費說明**：copilot CLI 走 GitHub Copilot 訂閱計費，與 Claude Code token 用量無關。
> Claude Code 的 token 消耗主要來自 Team Lead session 本身（讀檔、agent prompt、接收 agent 回應）。

## 變更一：加入 Gemini Reviewer

### 選用 Model：`gemini-2.5-flash`

| 考量 | 說明 |
|---|---|
| 推理能力 | Thinking model，能追蹤邏輯鏈，適合 code review |
| 上下文窗口 | 1M tokens，多檔案 diff 不截斷 |
| 穩定性 | 正式版（非 preview），rate limit 可靠 |
| 速度 | 與 GPT-4.1 / Claude 平行執行，速度夠用 |

**不選理由：**
- `gemini-3-flash-preview` / `gemini-3.1-flash-lite-preview` — preview 版 rate limit 嚴格，行為不穩定
- `gemini-2.5-flash` — 推理能力最弱，容易漏掉需要邏輯推理才能發現的 bug

### Gemini 差異化角色

| Reviewer | Model | Focus |
|---|---|---|
| copilot-reviewer | GPT-4.1 | bugs、security、concurrency、performance、edge cases |
| claude-reviewer | Claude | architecture、design patterns、maintainability、alternatives |
| **gemini-reviewer** | **gemini-2.5-flash** | **spec compliance、missing scenarios、edge case enumeration、requirement alignment** |

Gemini 的角色是「對需求規格掃描遺漏」，與前兩個 reviewer 視角完全不重疊。

### 新架構圖

```
User (Commander)
  │
Team Lead (current Claude session)
  │
  ├── copilot-developer  → copilot --model claude-sonnet-4.6 --allow-all-tools --autopilot
  │
  ├── copilot-reviewer   → copilot --model gpt-4.1 -p "..."
  │       Focus: bugs, security, performance, edge cases
  │
  ├── claude-reviewer    → Claude subagent (native)
  │       Focus: architecture, design patterns, maintainability
  │
  └── gemini-reviewer    → gemini --model gemini-2.5-flash -p "..."
          Focus: spec compliance, missing scenarios, requirement alignment
```

### Gemini CLI 呼叫格式

```bash
# stdin pipe 方式（需確認 Gemini CLI 支援）
cat $REVIEW_FILE | gemini --model gemini-2.5-flash -p "..." 2>&1

# 或 -p 直接嵌入內容
gemini --model gemini-2.5-flash -p "$(cat $REVIEW_FILE)\n\nReview the above..." 2>&1
```

> **待確認**：Gemini CLI 的 stdin pipe 行為是否與 Copilot CLI 相同。

## 變更二：Agent 間通訊壓縮協議

### 設計原則

> 只有最終產出（給使用者看的報告）和需求文件才需要人類可讀格式。
> Agent 與 Agent 之間的通訊只需要 AI 能解析即可。

### Inter-Agent Protocol v1

#### Review 報告格式（壓縮）

```
SRC:{model_id}
{severity}|{file:line_or_NA}|{issue_description}|{fix_suggestion}
VERDICT:{PASS|WARN|BLOCK}
```

**Severity codes：**
- `C` = critical（blocking issue，需修復才能合併）
- `W` = warning（應修復但不 blocking）
- `S` = suggestion（nice to have）

**範例：**
```
SRC:gpt-4.1
C|car_edit_page.dart:142|vehicleData null→crash|add null check before access
W|car_response.dart:58|fromJson empty array unhandled|add isEmpty guard
S|NA|extract validation to mixin for reuse
VERDICT:BLOCK
```

#### Task Dispatch 格式（壓縮）

```
TASK:{task_file_path}
```

#### Agent 回應格式

```
ACK                          # 收到任務，開始執行
DONE:{file1,file2,...}       # 完成，列出異動檔案
FAIL:{reason}                # 失敗原因
```

### Token 節省估算

> **計費範圍說明**：以下數字僅計算 Claude Code session 的 token 消耗。
> copilot CLI 走 GitHub Copilot 訂閱計費，與 Claude Code token 無關。

| 環節 | 現在（tokens） | 優化後（tokens） | 節省 |
|---|---|---|---|
| Agent prompt × 4 | ~1600 | ~600 | 63% |
| Review 報告 × 3 | ~1050 | ~240 | 77% |
| Task dispatch（單一大文件） | ~2000+ | ~150 × N 個小任務 | ~85% |
| Reviewer 讀檔（完整 source × N） | ~5000+ | diff 共用一份 | ~70% |
| CLI raw output 傳遞 | 全量貼上 | 只擷取 findings | ~60% |
| **每輪 cycle 總計（估算）** | **~9950+** | **~1600** | **~84%** |

### Team Lead 翻譯層

Team Lead 收到壓縮格式後，**只在呈現給使用者時**才轉成可讀格式：

```markdown
## Review 結果

### GPT-4.1 Review（bugs / security / performance）
❌ CRITICAL `car_edit_page.dart:142` — vehicleData 為 null 時 crash，需加 null check
⚠️ WARNING `car_response.dart:58` — fromJson 未處理空陣列

### Claude Review（architecture / maintainability）
✅ 架構合理，無 blocking issue
💡 SUGGESTION — 建議將驗證邏輯抽取成 mixin

### Gemini Review（spec compliance / missing scenarios）
⚠️ WARNING — 缺少 edge case：批次數量為 0 的情況未測試

**綜合判定：BLOCK**
需修復 1 個 critical issue 後再進行下一步
```

## 變更三：分層 Review 策略

### 三個 Level

```
Level 1 — 快速掃描（--quick）
  執行：gemini-reviewer only（gemini-2.5-flash）
  適合：typo fix、i18n key、小型 UI 調整
  耗時：~30 秒

Level 2 — 標準 Review（預設）
  執行：copilot-reviewer + claude-reviewer（平行）
  適合：一般功能實作、bug fix
  耗時：~2 分鐘

Level 3 — 深度 Review（--deep）
  執行：copilot-reviewer + claude-reviewer + gemini-reviewer（平行）
  適合：架構變更、高風險模組、核心邏輯修改
  耗時：~3 分鐘
```

### 指令範例

```bash
/ai-pair dev-team                    # Level 2（預設）
/ai-pair dev-team --quick            # Level 1
/ai-pair dev-team --deep             # Level 3
/ai-pair dev-team SSGS-11275 --deep  # 指定專案 + 深度 review
```

### Level 自動升級規則

```
Level 1 結果有 C → 自動升級到 Level 2（通知使用者）
Level 2 結果有 C 且影響核心模組 → 建議升級到 Level 3（詢問使用者）
```

## 變更四：其他優化項目

### 4a. 增量 Review（只送 diff）⚠️ 高優先

**問題**：多個 reviewer agent 各自獨立 Read 同一批 changed files，完整 source 被重複讀取 N 次。
實測：car wash module 共 5383 行，Level 3 review 時被讀了 3 次。

**解法**：Team Lead 在 dispatch review 前先生成 diff 檔，所有 reviewer 共用同一份 diff：

```bash
# Team Lead 產生 diff（只做一次）
DIFF_FILE=$(mktemp /tmp/review-diff-XXXXXX.txt)
git diff --no-color HEAD~1 > $DIFF_FILE

# 若有新建檔案（不在 diff 中），補充完整內容
git diff --no-color --name-only HEAD~1 | grep "^A" >> $DIFF_FILE

# 所有 reviewer 傳入相同 $DIFF_FILE 路徑
```

**Token 節省估算**：Level 3 review 的 input tokens 可減少 60-80%（視 diff 與 source 的大小比例）。

### 4b. Task 拆分 dispatch（單任務原則）⚠️ 高優先

**問題**：多個任務合批在單一大文件（實測 408 行 / 16KB），dispatch 時 copilot-developer 把整份文件讀入，包含所有已完成和待完成的任務。

**解法**：Team Lead 為每個任務產生獨立的小型 context file，依序 dispatch：

```bash
# 每個任務獨立一份 context file（~30-50 行）
TASK_FILE=$(mktemp /tmp/task-context-XXXXXX.md)
# 只寫入當前任務的 context，不包含其他任務

# dispatch 完成後立即刪除
rm -f $TASK_FILE
```

**規則**：
- 一次 dispatch 只包含一個任務
- 完成後再 dispatch 下一個任務
- 不合批多個任務到單一文件

### 4b. 自動 PASS/BLOCK 判定

Team Lead 解析所有 reviewer 的 `VERDICT` 後自動判定：

```
所有 reviewer VERDICT 均為 PASS → 自動標記 PASS，通知使用者確認
任一 reviewer VERDICT 為 BLOCK → 標記 BLOCK，需使用者決策
全為 WARN（無 BLOCK） → 標記 WARN，列出警告清單由使用者決定
```

### 4c. Review 結果快取

迭代修改時，若使用者已「修復 reviewer 指出的問題後重新 review」：

- Team Lead 在 task dispatch 中附上「上次 review findings」
- 告知 reviewer「以下是上次的問題，請確認是否已修復，並找出新問題」
- 減少 reviewer 重新掃描已確認正確的程式碼

### 4d. CLI 錯誤分級處理

| 錯誤類型 | 現在 | 優化後 |
|---|---|---|
| Rate limit | retry once → Claude fallback | 等 30 秒後重試 |
| Auth error | retry once → Claude fallback | 提示使用者重新登入 |
| Model unavailable | retry once → Claude fallback | 自動降級到 lite 版 |
| CLI not found | report error | 提示安裝指令 |

## 變更五：額度耗盡降級機制

### 設計原則

> 任何一個 reviewer 的免費額度耗盡，不應該卡住整個 review 流程。
> 跳過該 reviewer，用剩餘可用的 reviewer 繼續執行，最終報告標註缺少哪個視角。

### Agent 端：錯誤回報格式（Inter-Agent Protocol 擴充）

```
SRC:{model_id}
ERR:{error_code}|{raw_error_message}
```

錯誤碼定義：

| 錯誤碼 | 含義 | 典型觸發訊息 |
|---|---|---|
| `QUOTA` | 免費額度耗盡 | `429 Resource exhausted` / `quota exceeded` |
| `AUTH` | 認證失敗 | `401 Unauthorized` |
| `MODEL` | Model 不可用 | `model not found` / `not available` |
| `TIMEOUT` | CLI 執行逾時 | 超過設定的 timeout 無回應 |
| `CLI_MISSING` | CLI 未安裝 | `command not found` |

### Team Lead 端：降級決策邏輯

```
收到 reviewer 回報：

  正常（有 VERDICT）→ 正常處理

  ERR:QUOTA     → 標記 SKIPPED，繼續用剩餘 reviewer
  ERR:AUTH      → 提示使用者重新登入，繼續用剩餘 reviewer
  ERR:MODEL     → 走降級鏈，降級失敗也標記 SKIPPED
  ERR:TIMEOUT   → retry 一次，再失敗標記 SKIPPED
  ERR:CLI_MISSING → 標記 SKIPPED，提示安裝指令
```

### 降級鏈（Model Fallback Chain）

```
Gemini:  gemini-2.5-flash → gemini-2.5-flash → SKIP
GPT:     gpt-4.1 → gpt-4.1-mini → SKIP
Claude:  native subagent（無外部依賴，幾乎不會失敗）
```

### 最低可用門檻

| 可用 reviewer 數 | 行為 |
|---|---|
| 3 個 | 正常執行 |
| 2 個 | 繼續，報告標註缺少哪個視角 |
| 1 個 | 繼續，警告使用者 review 覆蓋率不足 |
| 0 個 | 中止，請使用者排除問題 |

因為 claude-reviewer 是 native subagent 不依賴外部 CLI，實務上至少保有 1 個 reviewer。

### 使用者看到的最終報告（有 reviewer 被跳過時）

```markdown
## Review 結果

### GPT-4.1 Review（bugs / security / performance）
❌ CRITICAL `car_edit_page.dart:142` — vehicleData null→crash，需加 null check

### Claude Review（architecture / maintainability）
✅ 架構合理，無 blocking issue

### Gemini Review
⏭️ **已跳過** — gemini-2.5-flash 免費額度耗盡（ERR:QUOTA）

---
⚠️ 本次缺少 Gemini 視角（spec compliance / missing scenarios）
建議額度恢復後用 `--deep` 重新執行完整 review
```
