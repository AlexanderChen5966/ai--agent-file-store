## 二、v4.2 的三個缺口

### 缺口 A：無任務類型維度的模式切換（🟡 中優先）

**現狀：** 模式選擇只有 `--quick / --deep`（按 review 深度），沒有「成本優先 vs 品質優先」維度。

使用者需要在呼叫前就決定：「這個任務值得花多少錢？」但目前沒有對應的旗標。

**Gap：** 
- 小功能修改 → 想省成本，但 `--quick` 只減少 reviewer 數量，不改 developer 使用的模型
- 高風險模組 → 想拉高品質，`--deep` 多了一個 reviewer，但 developer 還是 STANDARD tier

**提案：** 新增 `--economy / --quality` 旗標（不取代 `--quick / --deep`，是正交維度）

---

### 缺口 B：Developer 輸出無品質保底規則（🟡 中優先）

**現狀：** `copilot-developer` 收到 TASK_FILE 後自由執行，輸出後直接送 reviewer。

**Gap：** Reviewer 有時會花大量回應修正 developer 的**格式問題或模糊表達**，而非真正的邏輯問題。這相當於把品質控制的成本全部轉移給 reviewer。

**提案：** 在 developer 輸出後、送 reviewer 前，加入 Pilot Suite 的 **creator 品質保護規則**：
- 輸出超過 800 字 → Team Lead 要求 developer 精簡再送審
- 程式碼未附任何說明 → 要求補充變更摘要

這不是增加 reviewer，而是讓 developer 的輸出「值得被 review」。

---

### 缺口 C：Prompt Caching 未被主動利用（🟢 低優先）

**現狀：** Prompt Caching 是 Anthropic 自動觸發的機制（context 超過 1024 token 才啟用），SKILL.md 沒有任何針對性設計。

**Gap：** SKILL.md 本身超過 500 行，每次工作階段重新載入都是成本。但因為 Claude Code 的 cache 機制是透明的，不確定是否已自動生效。

**提案：** 低優先，留待 v4.5 實測後觀察 token 消耗再決定是否需要主動優化。

## 三、v4.5 核心變更

### 變更 A：新增呼叫模式旗標

```
/ai-pair dev-team [project]                  # 預設（同 v4.2）
/ai-pair dev-team [project] --economy        # 成本優先：所有角色使用 FREE tier
/ai-pair dev-team [project] --quality        # 品質優先：developer 使用 STANDARD，review level 升 3
/ai-pair dev-team [project] --quick          # 快速掃描（同 v4.2）
/ai-pair dev-team [project] --deep           # 深度審查（同 v4.2）
```

> `--economy` 和 `--quality` 可以和 `--quick / --deep` 組合：
> `/ai-pair dev-team --economy --quick` = 最省（FREE + 只跑 agy）
> `/ai-pair dev-team --quality --deep` = 最強（STANDARD + 三 reviewer）

**各模式的 Tier 可用範圍：**

模式旗標不直接指定模型，而是設定 Tier 上下限。Team Lead 在寫 TASK_FILE 時，依模式限制 + 任務複雜度動態決定最終 Tier。

| 模式 | Tier 可用範圍 | Team Lead 行為 |
|---|---|---|
| `--economy` | 只能用 `FREE` | 無論任務複雜度，Tier 鎖定 FREE |
| 預設（無旗標）| `LOW` ~ `STANDARD` | 簡單任務用 LOW，複雜任務用 STANDARD |
| `--quality` | `STANDARD` ~ `COMPLEX` | 底線是 STANDARD，高風險模組可升 COMPLEX |

**Tier → Developer 模型映射（複用 v4.2 現有設計）：**

| Tier | Developer 模型 |
|---|---|
| `FREE` | gpt-5-mini |
| `LOW` | gpt-5.4-mini |
| `STANDARD` | claude-sonnet-4.6 |
| `COMPLEX` | gpt-5.3-codex |

**copilot-reviewer / agy-reviewer 不變：**

| 模式 | copilot-reviewer | agy-reviewer |
|---|---|---|
| `--economy` | gpt-5-mini（FREE）| agy |
| 預設（無旗標）| gpt-4.1（FREE）| 不參與 |
| `--quality` | gpt-5.3-codex | agy |

### 變更 B：Developer 輸出品質保護

在 `Review Context Protocol Step 0` 之前，Team Lead 新增 **Output Quality Gate**：

```
收到 DONE:{files} 後，Team Lead 檢查：

1. developer 有無附上變更摘要？
   → 無 → SendMessage 要求補充（一行說明「改了什麼、為什麼」）

2. 輸出字數是否過長（> 800 字的說明文字，不含程式碼）？
   → 是 → SendMessage 要求精簡至核心論點

3. 是否標注了哪些邊界條件已處理、哪些未處理？
   → 無 → SendMessage 補充一行說明

通過以上三點後才進入 REVIEW_FILE 準備階段。
```

**效果：** Reviewer 的 findings 集中在邏輯/安全/規格問題，而非花時間補問基本資訊。

---

### 變更 C：TASK_FILE 加入 `Mode:` 欄位，`Tier` 由 Team Lead 動態決定

```markdown
# Task: {task name}

## Project Context
- Mode: ECONOMY | DEFAULT | QUALITY     ← 呼叫旗標帶入
- Tier: FREE | LOW | STANDARD | COMPLEX ← Team Lead 依 Mode 範圍 + 任務複雜度決定
...
```

**Team Lead 的 Tier 判斷規則：**

```
if Mode == ECONOMY  → Tier = FREE（強制，無論任務複雜度）
if Mode == DEFAULT  → Tier = LOW（簡單任務）
                      Tier = STANDARD（邏輯複雜、影響範圍廣）
if Mode == QUALITY  → Tier = STANDARD（一般任務）
                      Tier = COMPLEX（高風險模組：auth、core logic、payment）
```

此設計複用 v4.2 現有 Tier → 模型映射，不新增任何模型。模式旗標作為「Tier 可用範圍的約束條件」，Team Lead 在範圍內保留動態判斷能力。
