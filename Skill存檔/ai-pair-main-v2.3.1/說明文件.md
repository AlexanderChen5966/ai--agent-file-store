## 專案簡介

AI-Pair 是一個 **Claude Code Skill**，讓你可以協調多個異構 AI 模型組成團隊協作。

**核心概念：** 一個 AI 負責創作，另外兩個 AI（來自不同模型家族）負責從不同角度審查同一份工作。

這不是為了冗餘而設計的，而是利用不同模型天然關注不同維度的特性，讓每個模型做它最擅長的事。

---

## 核心理念

### 為什麼需要多個 AI 審查者？

大多數人使用多個 AI 的方式是：把同一個問題分別問一遍，然後對比答案。這種方式只使用了不同模型能力的一個維度。

AI-Pair 採取不同的做法：

| 傳統做法 | AI-Pair 做法 |
|---------|-------------|
| 同一問題 → 多個答案 | 同一份工作 → 多個視角 |
| 各自獨立回答 | 結構化角色分工 |
| 人工對比結果 | 自動彙總報告 |

### 不同模型的審查特性

根據實際觀察：

- **Claude**：發現來源引用的過度解讀、邏輯連貫性問題
- **GPT/Codex**：拆解論證鏈、質疑邏輯跳躍、安全性漏洞、邊界條件
- **Gemini**：架構設計、可讀性、受眾適配、整體可維護性

三者幾乎零重疊，這正是這套設計的價值所在。

## 系統架構

### 開發團隊（v2.3.0 新架構）

```
使用者（你）
  │
  ▼
團隊領導（當前 Claude Code 工作階段）
  │  職責：規劃任務、分析程式碼、產出任務文件
  │
  ├── copilot-developer（Claude Code Agent）
  │     └── 呼叫 → Copilot CLI（claude-sonnet-4.6，--allow-all-tools --autopilot）
  │           職責：依任務文件自主執行開發
  │
  ├── copilot-reviewer（Claude Code Agent）
  │     └── 呼叫 → Copilot CLI（gpt-4.1）
  │           職責：GPT 視角審查 — bugs、安全性、效能、邊界條件
  │
  └── claude-reviewer（Claude Code Agent）
        職責：Claude 視角審查 — 架構、設計模式、可維護性
```

### 內容團隊（不變）

```
使用者（你）
  │
  ▼
團隊領導（當前 Claude Code 工作階段）
  ├── author（Claude Code Agent）— 撰寫文章/腳本/Newsletter
  ├── copilot-reviewer（Claude Code Agent）— Copilot CLI（可選模型）
  └── claude-reviewer（Claude Code Agent）— Claude 第二視角
```

### 技術堆疊

| 元件 | 角色 | 說明 |
|------|------|------|
| Claude Code（當前 session） | 團隊領導 | 規劃、任務分析、協調 |
| Copilot CLI（claude-sonnet-4.6） | 開發者 | 自主讀取/編輯檔案、執行指令 |
| Copilot CLI（gpt-4.1） | GPT 審查者 | 邏輯安全性、邊界條件 |
| Claude Code Agent | Claude 審查者 | 架構設計、可維護性 |

## 前置條件

兩個工具都是**命令列工具**，需要在終端機中執行（Terminal、iTerm2 等），不是桌面應用程式。

### 安裝清單

```bash
# 1. 安裝 Claude Code
npm install -g @anthropic-ai/claude-code

# 2. 安裝 GitHub Copilot CLI
npm install -g @github/copilot-cli   # 或依官方文件安裝
```

### 驗證安裝

```bash
claude --version
copilot --version
```

兩個指令都必須正常回傳版本號，且都需要完成認證設定（GitHub Copilot 訂閱）才能使用。

| GPT-5 Mini | `gpt-5-mini` | 快速 GPT-5 |

## 使用方式

### 開發團隊模式

適用於：寫程式碼、修復 bug、重構

```bash
/ai-pair dev-team [專案名稱]

# 範例
/ai-pair dev-team b2b-manager
/ai-pair dev-team HighlightCut
```

**團隊成員：**

| 角色 | 工具/模型 | 職責 |
|------|----------|------|
| Team Lead | Claude（當前 session） | 規劃任務、分析程式碼、產出任務文件 |
| copilot-developer | Copilot CLI `claude-sonnet-4.6` + `--allow-all-tools` | 自主執行開發（讀取/編輯檔案、執行命令） |
| copilot-reviewer | Copilot CLI `gpt-4.1` | GPT 視角審查：bugs、安全性、效能、邊界條件 |
| claude-reviewer | Claude subagent | Claude 視角審查：架構、設計模式、可維護性 |

### 內容團隊模式

適用於：寫文章、腳本、Newsletter、任何創作任務

```bash
/ai-pair content-team [主題名稱]

# 範例
/ai-pair content-team AI-Newsletter
/ai-pair content-team ProductLaunchBlog
```

**團隊成員：**

| 角色 | 模型 | 職責 |
|------|------|------|
| author | Claude | 寫文章、腳本、Newsletter |
| codex-reviewer | GPT/Codex | 審查邏輯、準確性、結構、事實查核 |
| gemini-reviewer | Gemini | 審查可讀性、吸引力、風格、受眾適配 |

### 關閉團隊

```bash
/ai-pair team-stop
```

## 工作流程詳解

AI-Pair 採用**半自動工作流程** — 每一步你都保持完整控制權，不會有自動執行的迴圈。

### 完整流程（開發團隊）

```
步驟 1：你下達任務
        ↓
步驟 2：Team Lead 分析程式碼，產出任務文件（/tmp/task-context-XXXX.md）
        ↓
步驟 3：copilot-developer 收到任務文件，呼叫 Copilot CLI（claude-sonnet-4.6）自主開發
        ↓
步驟 4：Team Lead 回報開發結果（修改了哪些檔案），你決定是否送審
        ↓ （你批准）
步驟 5：copilot-reviewer（gpt-4.1）和 claude-reviewer 並行審查
        ↓
步驟 6：Team Lead 彙總審查報告呈現給你
        ↓
步驟 7：你決定
    ├── 「修改」→ 回到步驟 1（帶著審查意見）
    └── 「通過」→ 下一個任務或結束
```

### 審查報告格式

```
## Copilot 審查（GPT-4.1）

**來源：Copilot CLI gpt-4.1**

### CLI 原始輸出
{Copilot CLI 的完整輸出}

### 彙整評估

#### 重要（阻塞性問題）
- {描述 + 檔案:行號 + 建議修正}

#### 警告（重要問題）
- {描述 + 建議}

#### 建議（改進空間）
- {建議}

### 總結
{一句話品質評估}

---

## Claude 審查

**來源：Claude（架構與可維護性視角）**

### 架構問題
### 設計模式
### 可維護性
### 替代方案
```

## CLI 呼叫協定

### 開發者模式（copilot-developer）

copilot-developer 使用 `--allow-all-tools --autopilot`，讓 Copilot CLI 自主執行多步驟開發任務：

```bash
cat $TASK_FILE | copilot --model claude-sonnet-4.6 \
  --allow-all-tools \
  --autopilot \
  -p "You are a developer. Read the task context carefully and implement exactly what is described.
      Read the relevant files first before making any changes." \
  2>&1
```

- **逾時**：必須設定 **600000ms（10 分鐘）**，`--autopilot` 可能執行多輪繼續。
- **任務文件**：Team Lead 事先產出 `/tmp/task-context-XXXX.md`，copilot-developer 接收並執行。

### 審查者模式（copilot-reviewer）

copilot-reviewer 使用 stdin pipe + `-p` 非互動模式：

```bash
cat $REVIEW_FILE | copilot --model gpt-4.1 \
  -p "Review this code for bugs, security issues, performance, and edge cases.
      Be specific about file paths and line numbers. Output in Traditional Chinese." \
  2>&1
```

- **逾時**：設定 **300000ms（5 分鐘）**。
- **臨時檔案**：`REVIEW_FILE=$(mktemp /tmp/copilot-review-XXXXXX.txt)`，用完清理。

### 錯誤處理規則

| 情況 | 處理方式 |
|------|---------|
| CLI 未安裝 | 立即回報「Copilot CLI 未安裝」，**不得**自行替代 |
| 認證錯誤 | 回報確切錯誤訊息，重試一次 |
| 輸出含 ANSI 控制碼 | 呼叫前設定 `NO_COLOR=1` |
| 重試仍失敗 | 使用 Claude 備援，明確標示 `[Claude Fallback]` |

**核心原則：絕對不可靜默跳過 CLI 呼叫。**

## 代理人提示範本

### Developer 代理人（開發團隊）

職責：理解現有程式碼 → 實作功能/修復 bug/重構 → 回報變更 → 根據審查意見修改

工作規則：
- 修改前先理解現有程式碼
- 保持風格一致性
- 不過度設計
- 不確定時透過 SendMessage 向團隊領導確認

### Author 代理人（內容團隊）

職責：理解寫作任務 → 讀取 style-memory.md（若存在） → 撰寫內容 → 根據審查意見修改

工作規則：
- 簡潔直接
- 邏輯清晰
- 適當使用專業術語
- 遵循 style-memory.md 的風格偏好

### Codex 審查者代理人

**關鍵規則：** 必須使用 Bash 工具呼叫 `codex` 指令。你是派發者，不是審查者。不得自行審查，不得角色扮演 Codex。

開發團隊審查重點：
- Bug 和安全漏洞
- 並發/競態條件
- 效能問題
- 邊界條件

內容團隊審查重點：
- 邏輯連貫性
- 事實準確性
- 資訊架構
- 專業術語使用

### Gemini 審查者代理人

**關鍵規則：** 必須使用 Bash 工具呼叫 `gemini` 指令。你是派發者，不是審查者。不得自行審查，不得角色扮演 Gemini。

開發團隊審查重點：
- 架構設計
- 設計模式
- 可維護性
- 替代實作方案

內容團隊審查重點：
- 可讀性與流暢度
- 吸引力與開頭鉤子
- 風格一致性
- 目標受眾適配

## 使用範例

### 範例一：開發團隊 — 審查 Pull Request

**情境：** 為 /api/login 端點實作速率限制

```bash
/ai-pair dev-team my-web-app
```

下達任務：
```
為 /api/login 端點實作速率限制。
每個 IP 每 15 分鐘最多 5 次嘗試。
```

收到審查報告後：

**Codex 發現（安全/邊界條件）：**
- 速率限制鍵只用 IP 位址。在代理伺服器後面，所有使用者共享同一個 IP，考慮結合 IP + User-Agent 或使用 X-Forwarded-For
- 速率限制儲存器沒有清理過期記錄的機制
- 建議新增 X-RateLimit-Remaining 標頭

**Gemini 發現（架構）：**
- 記憶體內儲存器在多個伺服器實例下無法運作，考慮使用 Redis 或共享儲存
- 速率限制器與路由處理器緊耦合，應抽取為中介軟體以便複用

兩者完全不重疊 — Codex 發現安全邊界條件，Gemini 發現架構限制。

---

### 範例二：內容團隊 — 審查 Newsletter 文章

**情境：** 審查一篇關於 AI 記憶系統的 Newsletter 文章

```bash
/ai-pair content-team AI-Newsletter
```

收到審查報告後：

**Codex 發現（邏輯/準確性）：**
- 「LLMs 在工作階段之間沒有持久狀態」在技術上正確但過於簡化，建議加上「預設情況下」的限定詞
- 便利貼的類比有破綻：便利貼沒有檢索邏輯，MEMORY.md 更像是簡報文件
- 「200K tokens 的上下文視窗限制」應說明這是 Claude 的限制，GPT-4 Turbo 是 128K

**Gemini 發現（可讀性/結構）：**
- 開頭段落在讀者看到鉤子之前就用了三個專業術語，考慮先帶出相關情境
- 「便利貼」隱喻很有力但出現太晚（第 4 段），移到開頭效果更好
- 語氣在輕鬆（第 1-3 段）和學術（第 4-6 段）之間切換，目標受眾更適合輕鬆語氣

## 常見問題排查

### 問題：審查者沒有真正呼叫 Codex/Gemini CLI

**症狀：** 審查完成但只有 Claude Code 的用量在增加；Codex/Gemini CLI 用量沒有任何變化。子代理人在角色扮演而非真正呼叫外部 CLI。

**如何驗證：**
- 檢查審查輸出中是否有 `**Source: Codex CLI**` / `**Source: Gemini CLI**` 標籤
- 確認是否有 `### CLI Raw Output` 段落
- 如果缺失，表示 CLI 沒有被呼叫

**解決方式：**
1. 此問題已在 v1.1.0 中透過強制 CLI 呼叫規則修正，請更新至最新版 SKILL.md
2. 確認兩個 CLI 都已安裝：`codex --version`、`gemini --version`
3. 確認兩個 CLI 都已完成認證設定

### 問題：CLI 呼叫逾時

**症狀：** 審查過程中出現逾時錯誤

**解決方式：**
- 確認 Bash 工具呼叫設定了 `timeout: 600000`（10 分鐘）
- 若問題持續，審查者會自動降低 Codex 的推理等級重試

### 問題：輸出含有亂碼或 ANSI 控制碼

**症狀：** CLI 輸出中出現 `\e[32m` 等字元

**解決方式：** 在 CLI 呼叫前設定 `NO_COLOR=1`：

```bash
NO_COLOR=1 cat $REVIEW_FILE | codex exec "..." 2>&1
```
