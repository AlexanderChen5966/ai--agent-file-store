## 通用原則

**原則 1：不猜測，只標記**
遇到缺少欄位或語意不清，永遠標記給人處理，不自行補值。唯一例外：格式轉換（把段落改成清單）不改變內容語意。

**原則 2：一條只說一件事**
每個需求條目、每個參數說明，都必須是原子性的。「使用者可以篩選日期並匯出報表」要拆成兩條。

**原則 3：明確優先於簡潔**
寧可多寫一行「depends on: 使用者已登入」，也不讓 Agent 去猜前提條件。

**原則 4：只輸出 delta**
如果文件已有完整結構，不重新輸出整份文件，只輸出「有問題的部分」加上驗收報告。

## PRD 需求文件 SOP

### 必填欄位（缺少即標 ⚠️）

| 欄位 | 說明 |
|------|------|
| 功能名稱 | 明確的中文名稱 |
| 背景與動因 | 為什麼需要這個功能 |
| 影響範圍 | 哪些檔案、頁面、元件會被修改 |
| 詳細需求 | 具體的行為描述，含 UI 和邏輯 |
| 驗收條件 | 明確可測試的完成標準 |

### 選填欄位（缺少即標 💡）

| 欄位 | 補充原因 |
|------|---------|
| 不在範圍內 | 防止 Agent 做多 |
| API 變更說明 | 若涉及後端，Agent 需要知道契約 |
| 錯誤處理 | 邊界情況未說明，Agent 會自行決定 |
| 相依功能 | Agent 執行時可能破壞其他功能 |

### Layer 1 特別規則

- 「驗收條件」若只有「功能正常運作」→ ⚠️ 太模糊，無法測試
- 「影響範圍」若缺少具體檔案路徑 → 💡 建議補充，避免 Agent 猜路徑

### Layer 2 特別規則

PRD 常見歧義模式：

```
「若有需要」          → ⚠️ 條件不明確，何時「有需要」？
「參考設計圖」        → ⚠️ 設計圖不在文件內，Agent 看不到
「與現有功能一致」    → ⚠️ 哪個現有功能？哪些地方需一致？
「選擇 A 或 B」       → ⚠️ 需決定一個，或明確說明條件分支
「依照後端定義」      → ⚠️ 需引用具體 API 欄位，不能讓 Agent 自行查找
```

### Layer 3 特別規則

需求描述轉換示範：

```
原文：「在站別和品項之間新增類型下拉選單，選項需確認」
轉換後：
  1. MUST 在 [站別下拉] 和 [品項下拉] 之間插入 [類型下拉]
  2. ⚠️ 選項內容待確認：需提供 enum 值清單
  3. 類型下拉 尺寸 MUST 為 Size S
  4. Hint Text MUST 為「請選擇類型」
```

## API 文件 SOP

### 必填欄位（缺少即標 ⚠️）

每個 endpoint 都必須有：

| 欄位 | 說明 |
|------|------|
| HTTP Method | GET / POST / PUT / DELETE |
| Path | 完整路徑，含路徑參數 |
| 認證要求 | 是否需要 Bearer Token / x-group-id |
| Request 結構 | 每個參數的名稱、型別、必填/選填 |
| Response 結構 | 成功回傳的 JSON 結構 |
| 錯誤碼 | 常見錯誤碼與對應說明 |

### 選填欄位（缺少即標 💡）

| 欄位 | 補充原因 |
|------|---------|
| 情境範例 | Agent 生成呼叫代碼時需要具體範例 |
| 排序規則 | 若有 order_by 欄位，需說明可用值 |
| 分頁規則 | page/size 的預設值和上限 |
| Header 規範 | 除 Bearer Token 外的必要 Header |

### Layer 1 特別規則

- 參數表中有欄位沒有標示必填/選填 → ⚠️ 所有參數必須明確標示
- Response 只有範例沒有欄位說明 → 💡 建議補充欄位型別說明
- 缺少錯誤碼說明 → 💡 建議補充（Agent 需要知道 400 和 403 的處理方式不同）

### Layer 2 特別規則

API 文件常見歧義模式：

```
「String 或 null」       → ⚠️ null 是預設值還是代表特定意義？
「列表（可選）」          → ⚠️ 空列表 [] 和不傳 null 行為相同嗎？
「根據權限回傳」          → ⚠️ 哪些權限？不同權限回傳什麼？
「格式與前一版相同」      → ⚠️ 需明確引用，Agent 沒有版本記憶
「數值型別」              → ⚠️ 是 Int 還是 Long？可能溢位需要說清楚
```

### Layer 3 特別規則

參數表標準格式：

```markdown
| 欄位名稱 | 型別 | 必填 | 說明 | 範例值 |
|---------|------|------|------|--------|
| start_date | String | MUST | 查詢起始日期，格式 YYYY-MM-DD | "2026-01-01" |
| group_ids | List<Int> | OPTIONAL | 群組 ID 清單，null 表示查詢全部 | [1, 2, 3] |
| page | Int | MUST | 頁碼，從 1 開始 | 1 |
```

## ARCH 架構文件 SOP

### 必填欄位（缺少即標 ⚠️）

| 欄位 | 說明 |
|------|------|
| 適用範圍 | 哪些頁面或模組遵循此架構 |
| 核心元件 | 主要類別/檔案及其職責 |
| 資料流 | 資料從哪裡來、怎麼流動、存哪裡 |
| 使用規則 | MUST / MUST NOT 的明確約束 |

### 選填欄位（缺少即標 💡）

| 欄位 | 補充原因 |
|------|---------|
| 決策依據 | 為什麼這樣設計，Agent 才能在類似情況做對的選擇 |
| 不適用場景 | 明確說明何時不用此架構，防止 Agent 過度套用 |
| 參考實作 | 具體檔案路徑，讓 Agent 有範例可對照 |

### Layer 2 特別規則

架構文件常見歧義模式：

```
「類似的頁面使用相同架構」  → ⚠️ 「類似」的判斷標準是什麼？
「可以根據情況調整」        → ⚠️ 什麼情況？如何調整？需有決策樹
「通常繼承 CacheableState」 → ⚠️ 「通常」意味著有例外，需說明例外條件
「建議使用 X」              → ⚠️ 是強制還是建議？Agent 需要明確指令
```

### Layer 3 特別規則

決策規則轉換示範：

```
原文：「根據頁面功能需求選擇適當的模式」
轉換後：
  條件 1：頁面有複雜搜尋條件 + 需保留查詢狀態 → MUST 使用 CacheableState
  條件 2：頁面需要任務管理但無複雜搜尋 → MUST 使用 SingleTaskState
  條件 3：簡單展示頁面，無上述需求 → 使用 ConsumerState
```

## TASK Agent 任務文件 SOP

這是最重要的文件類型——直接決定 Agent 能不能正確執行任務。

### 必填欄位（缺少即標 ⚠️）

| 欄位 | 說明 |
|------|------|
| 任務目標 | 一句話說明成功完成是什麼樣子 |
| 輸入 | Agent 開始執行前需要的所有資訊 |
| 輸出 | Agent 執行後應該產生什麼（檔案、代碼、結果） |
| 執行步驟 | 編號的執行步驟，每步只做一件事 |
| 完成條件 | 可以客觀驗證的完成標準（非「功能正常」）|
| 約束條件 | MUST NOT 做的事 |

### 選填欄位（缺少即標 💡）

| 欄位 | 補充原因 |
|------|---------|
| 前置條件 | Agent 開始前需要確認的狀態 |
| 錯誤處理 | 遇到失敗時 Agent 應該做什麼 |
| 參考文件 | Agent 執行時可能需要查閱的文件 |
| 不在範圍 | 明確排除，防止 Agent 做多 |

### Layer 2 特別規則

任務文件是歧義容忍度最低的類型：

```
「依照現有風格」          → ⚠️ 需指定具體參考檔案路徑
「適當處理錯誤」          → ⚠️ 要 throw、catch、log、還是 fallback？
「與其他元件一致」        → ⚠️ 哪個元件？哪些地方要一致？
「如果需要的話」          → ⚠️ Agent 無法判斷「需要」，要給明確條件
「完成後通知」            → ⚠️ 怎麼通知？通知誰？用什麼方式？
步驟之間沒有說明依賴關係 → ⚠️ 步驟 3 是否依賴步驟 2 的輸出？
```

### Layer 3 特別規則

任務步驟標準格式：

```markdown
## 執行步驟

1. [動作] [對象] — depends on: 無
   - 輸入：XXX
   - 輸出：YYY
   - 完成標準：ZZZ

2. [動作] [對象] — depends on: 步驟 1 完成
   - 輸入：步驟 1 的輸出 YYY
   - 輸出：AAA
   - 若失敗：BBB
```

## 歧義判斷例庫

根據你的實際文件整理的常見歧義模式：

### 從你的需求文件中觀察到的

| 原文 | 問題 | 標記方式 |
|------|------|---------|
| 「需確認 Backend 定義或 Enum」 | enum 值未確認就進文件 | ⚠️ 需補充確認後的 enum 清單 |
| 「或者實作連動」 | 兩種方案都寫進去，未決定 | ❌ 邏輯衝突：需選擇方案 A 或 B |
| 「建議寬度設為 X 或與其他元件一致」 | 兩個標準不一定相同 | ⚠️ 需確認具體數值 |
| 「需改譯文」 | 有變更但沒說改成什麼 | ⚠️ 需補充新譯文內容 |
| 「需新增 Key 或組合字串」 | 兩種實作方式，未決定 | ⚠️ 需決定實作方式 |

### 從你的 API 文件中觀察到的

| 原文 | 問題 | 標記方式 |
|------|------|---------|
| 參數有「可選」但沒說 null 和空陣列的差異 | Agent 不知道該傳什麼 | ⚠️ 需說明 null vs [] 行為差異 |
| Response 只有範例 JSON，無欄位說明 | 缺少型別和 nullable 資訊 | 💡 建議補充欄位型別表 |

## 常見問題

**Q: 文件有些部分是給人看的說明，有些是給 Agent 的指令，混在一起怎麼處理？**
A: 在 Layer 3 重新格式化時，用 `> 說明：` 標記人類說明區塊，用正文或代碼塊標記 Agent 指令。不刪除說明，但要視覺上區分。

**Q: 文件裡有程式碼範例，要不要驗證代碼正確性？**
A: 不驗證代碼邏輯，只驗證代碼範例和文字說明是否一致。如果文字說「必填」但代碼範例裡傳 null，標 ❌ 邏輯衝突。

**Q: 需求文件裡有 UI 截圖描述但沒有附圖，怎麼處理？**
A: 標 ⚠️，說明「文件引用了圖片但未附上，Agent 執行時無法參考視覺設計」。

**Q: 同一份文件包含多個功能的需求，要分開處理嗎？**
A: 如果各功能的影響範圍完全獨立，建議拆成獨立文件。如果有相依關係，保持在同一文件但在 Layer 1 確認每個功能都有完整的必填欄位。

**Q: 發現文件描述的行為和我知道的系統行為不一致怎麼辦？**
A: 標 ⚠️ 說明「文件描述與[你觀察到的行為]不一致，需人工確認哪個是正確版本」。不自行決定哪個正確。
