## 專案簡介

AI-Pair 是一個 **Claude Code Skill**，用來協調多個異構 AI 模型組成團隊協作。

**核心概念：** 一個 AI 負責創作或開發，三個 reviewer 從不同角度審查同一份工作：

- **copilot-reviewer / GPT-4.1**：bugs、安全性、效能、邊界條件
- **claude-reviewer / Claude**：架構、設計模式、可維護性
- **gemini-reviewer / Gemini 2.5 Flash**：需求對齊、遺漏情境、spec coverage

這不是為了冗餘，而是把不同模型的偏好差異轉成結構化分工。

## 核心理念

### 為什麼需要多個 reviewer？

大多數人使用多個 AI 的方式是：把同一個問題分別問一遍，再人工比較答案。AI-Pair 的做法不同，它把同一份工作交給不同 reviewer，用不同視角找出互補問題。

| 傳統做法 | AI-Pair 做法 |
|---|---|
| 同一問題 → 多個答案 | 同一份工作 → 多個視角 |
| 各自獨立回答 | 結構化角色分工 |
| 人工對比結果 | Team Lead 彙整結論 |

### reviewer 差異化角色

| Reviewer | Model | Focus |
|---|---|---|
| copilot-reviewer | GPT-4.1 | bugs、security、concurrency、performance、edge cases |
| claude-reviewer | Claude | architecture、design patterns、maintainability、alternatives |
| gemini-reviewer | gemini-2.5-flash | spec compliance、missing scenarios、requirement alignment |

## 系統架構

### 開發團隊

```
使用者（你）
  │
  ▼
Team Lead（當前 Claude Code session）
  │  職責：讀碼、規劃、產出 task file、建立 shared review file、彙整 reviewer 結果
  │
  ├── copilot-developer（Claude Code Agent）
  │     └── 呼叫 Copilot CLI（claude-sonnet-4.6）
  │           職責：依 task context 實作
  │
  ├── copilot-reviewer（Claude Code Agent）
  │     └── 呼叫 Copilot CLI（gpt-4.1）
  │           職責：bugs / security / performance / edge cases
  │
  ├── claude-reviewer（Claude Code Agent）
  │           職責：architecture / maintainability / alternatives
  │
  └── gemini-reviewer（Claude Code Agent）
        └── 呼叫 Gemini CLI（gemini-2.5-flash）
              職責：spec compliance / missing scenarios / requirement alignment
```

### 內容團隊

```
使用者（你）
  │
  ▼
Team Lead（當前 Claude Code session）
  ├── author（Claude Code Agent）— 撰寫內容
  ├── copilot-reviewer（Copilot CLI / GPT-4.1）— 邏輯、準確性、結構
  ├── claude-reviewer（Claude）— 可讀性、風格、受眾適配
  └── gemini-reviewer（Gemini CLI）— 完整性、缺漏、主題對齊
```

### Review Levels

| Level | 指令 | reviewer 組合 | 適用情境 |
|---|---|---|---|
| Level 1 | `--quick` | Gemini only | typo、小 UI 調整、低風險微調 |
| Level 2 | 預設 | Copilot reviewer + Claude reviewer | 一般功能與 bug fix |
| Level 3 | `--deep` | GPT + Claude + Gemini | 架構變更、高風險模組、核心邏輯 |

### 自動升級規則

- Level 1 有 `CRITICAL` → 自動升級到 Level 2
- Level 2 有 `CRITICAL` 且影響核心模組 → 建議升級到 Level 3

## 工作流程詳解

### 開發團隊完整流程

1. 使用者下達任務
2. Team Lead 讀取相關檔案，必要時只問一個釐清問題
3. Team Lead 只拆出單一任務，產生一份 `TASK_FILE`
4. copilot-developer 依 `TASK:{path}` 執行實作
5. Team Lead 回報 `DONE:{files}`，由使用者決定是否送審
6. 若送審，Team Lead 建立一份共享 `REVIEW_FILE`
7. reviewer 依 review level 並行審查
8. Team Lead 收集壓縮格式輸出並翻譯成使用者可讀報告
9. 使用者決定修改、通過、或升級 review level

### 單任務 dispatch 原則

- 一次 dispatch 只包含一個任務
- 不把多個任務合併到同一個 context file
- 當前任務結束後，才建立下一個 task file

### diff-only review 原則

送 reviewer 前，Team Lead 先建立一份共享 review file：

```bash
REVIEW_FILE=$(mktemp /tmp/review-XXXXXX)
git diff --no-color HEAD~1 > "$REVIEW_FILE"
```

規則：

- reviewer 共用同一份 `REVIEW_FILE`
- 只在 diff 不足時補最小必要上下文
- re-review 時可附上 `Previous findings`，要求 reviewer 驗證是否修正
- Team Lead 透過 SendMessage 傳送 `REVIEW:{path}` 給各 reviewer；reviewer **不得**自行 Read/Glob/Grep source files

### Review 結果快取

快取目的：同一任務迭代修正時，reviewer 先驗證舊問題是否修復，再找新問題，不必從零掃描。

```
快取路徑（不進 Git）：.ai-pair-cache/review-findings/{task_id}.md
```

**流程：**

1. **Step 0（建立 REVIEW_FILE 前）**：若快取存在且條件符合（同 task id / reviewer 組合 / review level / 48h 內），讀取並設 `HAS_CACHE=true`
2. **Step 3**：`HAS_CACHE=true` 時，將快取 findings 附加為 `Previous findings` 段落到 REVIEW_FILE 開頭
3. **Step 6（所有 reviewer 回報後）**：
   - 綜合判定 PASS → 刪除快取
   - WARN / BLOCK → 將本輪 findings 寫入快取，供下次 re-review 使用

**快取清除條件**：PASS、task id 改變、需求轉向、修改範圍大幅擴大、review level 改變、reviewer 組合改變、48 小時未使用

## Inter-Agent Protocol

### Review Report

```text
SRC:{model_id}
{severity}|{file:line_or_NA}|{issue}|{fix}
VERDICT:{PASS|WARN|BLOCK}
```

Severity：

- `C` = critical
- `W` = warning
- `S` = suggestion

### Error Report

```text
SRC:{model_id}
ERR:{code}|{raw_message}
```

錯誤碼：

- `QUOTA`
- `AUTH`
- `MODEL`
- `TIMEOUT`
- `CLI_MISSING`

### Task Dispatch / Agent 回報

```text
TASK:{file_path}
ACK
DONE:{file1,file2,...}
FAIL:{reason}
```

### Team Lead 自動判定

- 全部 `VERDICT:PASS` → PASS
- 任一 `VERDICT:BLOCK` → BLOCK
- 全部為 WARN 且無 BLOCK → WARN

## Review 結果快取

### 用途

快取的目的是讓同一任務的 re-review 不必從零開始，不是要跳過 review。

Team Lead 會沿用上一輪 findings，要求 reviewer：

- 先驗證舊問題是否已修復
- 再找這次 diff 的新問題

### 本機快取路徑

Review 結果快取只給「同一個人、同一台機器、同一工作區」迭代修正使用，不進 Git。

```text
.ai-pair-cache/
  review-findings/
    {task-id}.md
```

### 快取內容

- task id
- review level
- reviewer 組合
- 上一輪 changed files
- 正規化後的 findings 摘要
- review timestamp

### 何時寫入快取

- 一輪 review 正常完成後
- 至少有一個 reviewer 回傳 `VERDICT`
- 只保存 findings 摘要，不保存 raw CLI output

### 何時可以重用

- 同一個 task id
- 同一個 workspace
- 同一 reviewer 組合
- 同一 review level，或更窄的覆蓋範圍
- 48 小時內
- 本輪仍是小幅迭代修正

### 何時必須清除

- 使用者確認任務 PASS / 完成
- task id 改變
- 需求方向改變
- 修改範圍明顯擴大
- review level 改變，例如 `--quick` 升到預設或 `--deep`
- reviewer 組合改變
- 48 小時未使用
- Team Lead 無法判定快取是否仍安全可用

### 重用流程

1. Team Lead 讀取 `.ai-pair-cache/review-findings/{task-id}.md`
2. 在 `REVIEW_FILE` 前面附上 `Previous findings`
3. reviewer 先確認舊問題是否已修復
4. reviewer 再檢查本輪 diff 是否引入新問題
5. 本輪 review 完成後覆蓋舊快取

## CLI 呼叫協定

### copilot-developer

```bash
cat $TASK_FILE | copilot --model claude-sonnet-4.6 \
  --allow-all-tools --autopilot \
  -p "You are a developer. Implement exactly what the task context describes.
      Read relevant files first. Follow constraints strictly.
      Do NOT run git commands. Output summary in Traditional Chinese." \
  2>&1
```

- timeout：`600000`
- 失敗時重試一次
- 仍失敗則回報 `FAIL:{reason}`

### copilot-reviewer

```bash
cat $REVIEW_FILE | copilot --model gpt-4.1 \
  -p "Review for bugs, security, concurrency, performance, edge cases.
      Output ONLY in compressed format." \
  2>&1
```

- timeout：`300000`
- `TIMEOUT` 可重試一次
- 不得自行用 Claude 替代 GPT review

### gemini-reviewer

```bash
cat $REVIEW_FILE | gemini --model gemini-2.5-flash \
  -p "Review this code for spec compliance, missing scenarios, requirement gaps, edge cases.
      Output ONLY in compressed format." \
  2>&1
```

- timeout：`300000`
- `MODEL` 時可降級到 `gemini-2.5-flash-lite`
- `flash-lite` 可能用 `/` 分隔 findings，Team Lead 需容錯解析

### 錯誤處理與降級鏈

| 類型 | Team Lead 行為 |
|---|---|
| `QUOTA` | 標記 SKIPPED，繼續 |
| `AUTH` | 提示重新登入，繼續 |
| `MODEL` | 嘗試 fallback |
| `TIMEOUT` | 重試一次，再失敗則 SKIP |
| `CLI_MISSING` | 提示安裝指令 |

Fallback chain：

```text
Gemini: gemini-2.5-flash → gemini-2.5-flash-lite → SKIP
GPT:    gpt-4.1 → gpt-4.1-mini → SKIP
Claude: native subagent
```

## 常見問題排查

### reviewer 沒有真正呼叫外部 CLI

症狀：

- 只有 Claude Code 用量上升
- Copilot CLI / Gemini CLI 沒有任何呼叫痕跡

處理：

1. 確認 `copilot --version`、`gemini --version`
2. 確認已登入
3. 確認 `.claude/settings.local.json` 已允許 CLI 指令
4. 檢查 reviewer 是否真的回傳壓縮格式，而不是自由 prose

### Gemini 額度耗盡

處理：

- 標記 `ERR:QUOTA`
- 以剩餘 reviewer 繼續
- 建議之後用 `--deep` 重跑完整 review

### timeout

處理：

- reviewer 先重試一次
- 若仍失敗，標記 `ERR:TIMEOUT`

### macOS 上 `mktemp` 無法產生隨機檔名

**症狀：**

`mktemp /tmp/task-XXXXXX.md` 或 `mktemp /tmp/review-XXXXXX.txt` 直接輸出原始樣板字串（X 不展開），導致後續 `cat > "$TASK_FILE"` 寫入固定路徑或失敗。

**原因：**

macOS（BSD）的 `mktemp` 不支援在 X 後面接副檔名。X 必須出現在字串最尾端，否則不展開。

**解法（擇一）：**

```bash
# 方法 1：移除副檔名（推薦，最簡單）
TASK_FILE=$(mktemp /tmp/task-XXXXXX)

# 方法 2：python3 fallback（需要 python3）
TASK_FILE=$(python3 -c "import tempfile; f=tempfile.NamedTemporaryFile(suffix='.md',dir='/tmp',delete=False); print(f.name); f.close()")
```

SKILL.md 範例已統一修正為不帶副檔名的格式。
