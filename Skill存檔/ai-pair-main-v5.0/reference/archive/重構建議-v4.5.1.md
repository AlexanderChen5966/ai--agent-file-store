## 一、為什麼是 Optional

OpenRouter Fusion 是一套商業化的「多模型協同審議」服務：一個 prompt 平行丟給 panel（最多 8 模型），再由 judge model 比對所有回答、輸出結構化分析（consensus / contradictions / coverage gaps / unique insights / blind spots），最後合成答案。

**它跟 ai-pair 看似相同，實則優化不同的東西**——這是判斷「要不要借」的關鍵：

| | OpenRouter Fusion | 現有 ai-pair |
|---|---|---|
| panel 收到的 prompt | **同一個** prompt 給所有模型 | **不同角色** prompt（spec / security / logic 各看一面） |
| 優化目標 | 降低**單一模型隨機錯誤**（多模型收斂） | 提高**審查維度覆蓋**（不同視角抓不同問題） |
| judge 工作 | 比對「同題不同模型」共識與矛盾 | 彙整「不同題不同角色」的 findings |
| 成本 | 4～5×，**無免費模型** | 跨平台分散額度，FREE tier 可零成本 |

**結論：** Fusion 不是 ai-pair 的替代品，兩者互補。若直接用 Fusion 同質 panel 取代角色分工 reviewers，反而**失去 ai-pair 最值錢的角色分工審查**。因此本文件只借**概念**，不接**產品**，且全程選用。

## 二、嚴格不變更的部分（採用本方案時的紅線）

採用 v4.5.1 時，以下一律**不動**：

- ❌ 不取代 agy / opencode / copilot 的 CLI fan-out 架構
- ❌ 不取消角色分工 reviewers（copilot-reviewer / claude-reviewer / gemini-reviewer 各自視角）
- ❌ 不取消跨供應商分散額度（天然優勢）
- ❌ 不取消 FREE tier 免費模型池（v4.4）
- ❌ 不取消 48h Review Cache
- ❌ 不引入 OpenRouter 帳單依賴（除非選用「增強 C」）

v4.5.1 只新增 Team Lead 彙整層的**輸出格式與一個自檢步驟**，屬純 prompt 改動。

## 三、借鑑內容（三個增強，全部 Optional 且可獨立啟用）

### 增強 A：Judge 輸出 schema 升級（🟢 最高 CP，純 prompt，零成本）

**現狀：** Team Lead Translation Layer 收到各 reviewer 的壓縮 findings 後，彙整成人類可讀報告 + 總 `VERDICT`。但**沒有明確標出**：
- reviewers **彼此矛盾**之處（A 說 PASS、B 對同一行說 BLOCK）
- 各 reviewer 的**獨特見解**（只有一個人抓到、但很關鍵）

**借鑑 Fusion 的 judge schema，升級 Team Lead 的彙整輸出：**

```
### Team Lead 綜合審查（v4.5.1 schema）

**1. CONSENSUS（共識）**
   多數 reviewer 一致認同的 findings（信心最高，優先處理）
   - {finding} ← copilot, claude, gemini 皆標記

**2. CONTRADICTIONS（矛盾）**  ← 新增
   reviewers 對同一處給出不同 verdict 的項目（需 Team Lead 裁決）
   - {file:line}: copilot=PASS / claude=BLOCK → 裁決：{理由}

**3. UNIQUE INSIGHTS（獨特見解）**  ← 新增
   只有單一 reviewer 抓到、但具關鍵性的 findings
   - {finding} ← 僅 claude 標記，但屬 security critical

**4. COVERAGE GAPS（覆蓋缺口）**  ← 新增，見增強 B
   無人覆蓋的維度

**VERDICT:** PASS | WARN | BLOCK（綜合上述後決定）
```

**效益：** 矛盾不再被靜默彙平（現狀可能 3 票取多數而忽略少數的正確警告）；獨特見解不被淹沒。**不增加任何 CLI 呼叫**。

---

### 增強 B：Blind-spot Pass（🟡 中 CP，概念價值最高）

**現狀的致命弱點：** 三個 reviewer 若**共享同一個盲點**（例如都沒注意到某 Flutter Web / WASM 限制、都漏掉某 OAuth2 PKCE 邊界），現有彙整層**永遠不會發現**——因為它只彙整「有人提出的」，不問「沒人提出的」。

**借鑑 Fusion 的 blind-spot 偵測，在 Team Lead 彙整後新增一步自檢：**

```
彙整完所有 reviewer findings 後，Team Lead 額外自問一輪：

「以下高風險維度，是否『沒有任何 reviewer』提及？」
  □ OAuth2 / TaskManager 流程是否被觸及而無人審查？
  □ DataTable2 sortColumnIndex / fixedWidth 是否被改而無人檢查？
  □ screenutil（.w/.h/.sp）是否被新增而無人標記？
  □ 是否有 Flutter Web only 不支援的 mobile-only 寫法？
  □ build_runner 必執行路徑是否被改而無人提醒？

任一項「被觸及但無人審查」→ 列入 COVERAGE GAPS，VERDICT 至少 WARN
```

> 註：上列檢查點直接對應本專案 CLAUDE.md / AGENTS.md 的高風險紅線，
> 等於把專案規則變成 Team Lead 的盲點清單，補 reviewer 共同盲區。

**效益：** 把「沒人抓到的」變成可見的 COVERAGE GAPS。成本只是 Team Lead 一次額外推理，無 CLI 呼叫。

---

### 增強 C：Fusion 作為 `--quality` 頂層可選後端（🔵 低 CP，需 OpenRouter 帳號，完全選用）

**僅在以下全部成立時才考慮：**
- 任務屬最高風險（auth / core logic / payment）
- 使用者明確下 `--quality --deep`
- 使用者**主動**接受 4～5× 成本與 OpenRouter 帳單依賴

**接法：** 不取代現有 reviewers，而是**多加一個**「fusion-reviewer」角色，僅在上述條件觸發：

```bash
# 僅 --quality --deep + 使用者明確啟用 FUSION 時呼叫
curl https://openrouter.ai/api/v1/chat/completions \
  -d '{
    "model": "openrouter/fusion",
    "messages": [{"role":"user","content":"<REVIEW_FILE 內容 + 審查指令>"}],
    "analysis_models": ["anthropic/claude-opus", "openai/gpt-5.4", "google/gemini-pro"]
  }'
```

**定位：** Fusion 是 Tier 系統**最頂端的一個選項**，預設關閉。`--economy` 模式**永遠不得**啟用（成本方向相反）。

| 模式 | reviewer 後端 |
|---|---|
| `--economy` | opencode 免費模型（v4.4），❌ 禁用 Fusion |
| 預設 | 現有 CLI 角色分工 reviewers |
| `--quality --deep` + 使用者啟用 | 現有 reviewers **＋** 可選 fusion-reviewer |

## 四、採用建議

| 增強 | 建議 | 成本 | 風險 |
|---|---|---|---|
| A：Judge schema 升級 | ✅ **建議採用** | 零（純 prompt） | 極低 |
| B：Blind-spot Pass | ✅ **建議採用** | 一次額外推理 | 極低 |
| C：Fusion 後端 | ⚪ **預設不採用** | 4～5×＋帳單 | 中（外部依賴） |

**最小落地路徑：** 只採 A + B，完全不碰 OpenRouter，零外部依賴、零增量成本，就能補上「矛盾彙平」與「共同盲點」兩個現有弱點。C 留作未來高風險任務的選配。
