## 一、為什麼要改

起因是一次具體的選擇題：某個功能分支的 code review，判斷應該用 `stack-review` 而非 ai-pair。追究理由時發現，ai-pair 的弱勢**不是設計理念問題**——多模型異質 review 的前提是成立的——而是把 agentic CLI 當成純文字管道使用，導致 reviewer 失去查證能力。

### 1.1 模型命名慣例分歧，以及一條過期的限制描述

⚠️ **本節已依 E1 實測大幅下修。** 初稿主張「模型名稱全錯」，實測證明錯誤。

**實測結論（`phase-v5-cli-probe.md` E1）：**

agy **同時接受兩種命名格式**，兩者皆有效、指向同一組模型：

| 格式 | 範例 | 來源 |
|---|---|---|
| slug | `gemini-3.1-pro-high` | `agy models` 的輸出 |
| 顯示名 | `Gemini 3.1 Pro (High)` | 錯誤訊息的 Available models 清單、**skill 現行寫法** |

因此 **skill 的 agy 模型設定是有效的，`gemini-reviewer` 並未跑錯模型**。E3 同樣確認 skill 指定的 copilot 模型名稱**全部有效**。

**仍然成立、且值得處理的部分：**

**① v4.3 的「靜默降級」Known Limitation 已過期。**
實測 agy v1.1.8 對無效模型明確回 `status:"ERROR"`、附可用清單、**零 token 消耗**。該限制描述應標為「已於 v1.1.8 修正」，而非繼續作為設計依據——它目前正誤導 `ERR:MODEL` 的處理邏輯（見 §4.2）。

**② 兩個 CLI 的命名慣例相反，是真實的踩雷點。**

```
copilot:  claude-haiku-4.5      claude-sonnet-4.6      ← 用「點」
agy slug: claude-sonnet-4-6     claude-opus-4-6-thinking ← 用「連字號」
```

跨 CLI 套用同一拼法會失敗。實測時 `claude-haiku-4-5` 被 copilot 拒絕，改 `claude-haiku-4.5` 即可用。文件須明確標示各 CLI 的慣例。

> 📌 **本節的真正教訓不在模型名稱，而在推論方法。**
> 初稿看到「`agy models` 輸出 slug」就推論「顯示名無效」，再疊上一條**過期的** Known Limitation（靜默降級），得出「reviewer 一直跑錯模型」的結論——**三層推論，零實測**。
> 而那條 Known Limitation 本身就是「記下來就收工、沒有再驗證」的產物。
> **對策不只是修文件，而是：涉及外部 CLI 行為的主張，一律先實測再寫入**（§7 的實測計畫因此前置於所有實作）。

### 1.2 🔴 把 agentic CLI 當成 dumb text pipe（最嚴重）

`copilot` 與 `agy` 都是**具備檔案工具的 agent**，不是 text completion endpoint。但現行 Review Context Protocol 的整個設計都在解「怎麼把 payload 灌進 prompt」這個問題：

- v4.3.5 花了整份提案處理「Copilot CLI 不讀 stdin，任務內容必須讀進變數嵌入 `-p`」
- 由此衍生 `SKILL.md:434` 的自我限制：*"Reviewers must NOT read source files on their own — REVIEW_FILE is their only input"*

**後者是真正的傷害。** 它廢掉了跨檔案與跨 repo 查證能力，而那恰好是 ai-pair 輸給 stack-review 的主因。對照最近一次 `stack-review` 實際抓到的 findings：

| finding | 需要什麼才看得到 |
|---|---|
| 前端權限清單與後端 `Role.java` 是否逐字一致 | 讀**另一個 repo** 的原始碼 |
| 註解聲稱走某方法，但該方法**從未被呼叫** | 全專案 grep |
| 某工廠方法是 static，導致無法注入 mock | 讀 diff 範圍外的既有檔案 |
| 分頁實作是否與既有頁面 pattern 一致 | 讀另一個模組的實作對照 |

**這四項在 diff 裡全部隱形。** 三個看不到原始碼的 reviewer，弱於一個能 grep 全專案的 reviewer——reviewer 數量的優勢被輸入品質的劣勢抵銷還倒賠。

### 1.3 硬編碼的維護負擔

| 檔案 | 硬編碼模型名稱處數 |
|---|---|
| `SKILL.md` | 38 |
| `README.md` | 31 |
| `reference/cli-invocation-ref.md` | 20 |
| 8 份「重構建議」歷史文件 | 其餘約 110 |

共 17 個 .md、200+ 處。模型清單一動就整套過期，而供應商換模型的頻率遠高於這份文件的維護頻率。

**佐證：** copilot 的系統預設模型已是 `gpt-5.6-terra`（使用者選用 `claude-sonnet-5`），catalog 另有 Grok 4.5、Kimi K2.7 Code 等 skill 完全未提及的模型；而 skill 仍在指定 `gpt-5.4-mini` / `claude-sonnet-4.6`。更關鍵的是**計費模式已於 2026-06-01 改制**，Tier 表的 Credits 數值全部失效（見 §1.4 末列）。

### 1.4 兩個 CLI 都已新增對症的能力

現行文件寫的限制多半基於較舊版本（copilot 限制記於 v1.0.65，現為 **v1.0.75**；agy 現為 **v1.1.8**）。實際上：

| 能力 | 解決什麼 |
|---|---|
| `agy models` 子命令 | 列出 slug 格式模型清單（⚠️ 只有 slug，不含顯示名，見 §4.2） |
| agy `--json-schema` | 強制結構化輸出，不再靠模型自律遵守壓縮格式 |
| agy `--output-format json/stream-json` | 可靠解析、token 用量可歸因（含 `cache_read_tokens`） |
| agy `--add-dir`、`--sandbox` | reviewer 可讀取指定目錄。🔴 **但 `--add-dir` 只給檔案讀取權**；shell 工具（grep/glob）在 headless 需 `--dangerously-skip-permissions`，否則自動拒絕（E7） |
| copilot `--add-dir` | reviewer 可讀專案與**後端 repo** |
| copilot `--max-ai-credits` | **直接封住「空跑燒 Credit」** |
| copilot `-s / --silent` | 只輸出 agent 回應。🔴 **不保證乾淨**——多步驟工具呼叫時過程敘述會混入，JSON 在尾端，須抽取（E6-bis） |
| copilot `--output-format json` | JSONL 可靠解析 |
| copilot `--model auto` | 交給 Copilot 自行路由，作為 fallback 終點 |
| 兩者 `--effort` | 深度不必靠換模型（copilot 至 `max`，agy 至 `high`） |
| Copilot 改 usage-based billing（2026-06-01） | multiplier 制廢除，改按供應商 list price 計 token → **Tier 表數值全部過期**，且應改為引用官方費率（見 `phase-v5-cli-probe.md` E5） |

## 二、嚴格不變更的紅線

採用 v5.0 時，以下一律**不動**：

- ❌ 不取消角色分工 reviewers（各自視角，這是 ai-pair 最值錢的部分）
- ❌ **reviewer 不得作為預算調節閥**——多 reviewer 的存在目的就是維護品質；依任務風險調整數量可以，依預算壓力削減不行（見 §3.6）
- ❌ **claude-reviewer 不可省略**——developer 與探索都外包後，它是唯一的獨立驗證環節（見 §3.6、§4.5.4）
- ❌ 不取消跨供應商分散額度的天然優勢
- ❌ 不取消 48h Review Cache 機制
- ❌ 不取消「需求文件必須存在」的前置條件
- ❌ **不弱化 Bias Mitigation**（`SKILL.md:341-350`）——詳見 §3.9，統籌者變強時這條反而更重要
- ❌ **不移除 copilot-developer**——它在 v5.0 是 developer 的**預設**引擎（見 §3.3）
- ❌ **developer 模型不得降至 LOW/FREE tier**（見 §4.5.1）
- ❌ 不引入新的付費依賴

## 三、架構決策：統籌者與 worker 的分工

### 3.1 決策

**Claude 額度只花在「協調決策」與「review 驗證」兩處；探索與實作常態外包給 external CLI。**

| 角色 | v4.3.6 引擎 | v5.0 引擎 | 變更 |
|---|---|---|---|
| Team Lead | 當前 session（隱含） | 當前 session（**明定**） | 從隱含改為顯式規格 |
| **explorer** | （無此角色） | **external CLI（常態）** | 🆕 新增角色 |
| developer | copilot CLI (`claude-sonnet-4.6`) | **copilot CLI（預設）／native subagent（品質升級）** | 🔄 改為雙引擎，預設仍為 copilot |
| claude-reviewer | native subagent | native subagent | **保留且強化**，解除「不得讀 source」禁令 |
| copilot-reviewer | copilot CLI | copilot CLI | 保留，模型改動態解析 |
| gemini-reviewer | agy CLI | agy CLI | 保留（模型名稱**無需修正**，E1 已證現行設定有效） |

> ⚠️ **本節經兩次修正，記錄推導過程以免日後誤解：**
> - **初稿**：提議移除 copilot-developer、implementation 全收回 native。理由是「故障面最小」。
> - **修正一**：Claude 額度是硬性運維限制，備援必須保留 → 改為雙引擎。
> - **修正二（本版）**：進一步發現初稿把**資源稀缺性**排在故障面之後，順序搞反了 → **copilot-developer 改回預設**，native 降為品質升級路徑；並新增 explorer 角色，把 Team Lead 的探索工作也外包。

### 3.2 為什麼 copilot 當預設引擎：保護不可替代的資源

決策依據不是「哪個引擎品質好」，而是**哪個資源不可替代**。

| 資源 | 耗盡後果 | 可替代性 |
|---|---|---|
| **Claude 額度** | Team Lead 停擺 → **整個流程停止**，無任何 fallback 能救（見 §3.4） | ❌ 不可替代 |
| Copilot Credits | developer 降級回 native | ✅ 可替代 |
| agy 免費額度 | 少一個 reviewer 視角 | ✅ 可替代 |

> ⚠️ **保留 agy 的理由已依實測改寫**：E3 補測發現 copilot 單一 CLI 已涵蓋 **GPT／Claude／Gemini／Grok／Kimi 五個模型家族**，因此「模型家族多樣性」不再需要 agy。agy 剩下的不可取代價值是**跨供應商分散額度**（三個 reviewer 全走 copilot 會共用同一 Credit 池）與**免費額度**（官方費率表確認 copilot **無任何免費模型**）。

把稀缺且不可替代的資源，花在**有替代品的任務**上，是反向配置。

**Claude 額度的邊際價值排序**（決定該優先花在哪）：

1. **Team Lead — 協調、判斷、決策**：不可替代，最高優先
2. **claude-reviewer — 跨檔案／跨 repo 查證**：native subagent 工具權限最完整，external CLI 即使加了 `--add-dir` 也差一截
3. **explorer — 探索**：可外包（見 §3.5）
4. **developer — 實作**：**最該外包**，這是唯一有成熟替代品的角色

> 佐證（既有實測紀錄）：copilot-developer 的優勢在「需求模糊需自行判斷」與「多檔案同時大幅改寫」；而「同一 pattern 重複套用」的任務直接實作更快更精確。後者是 native 的升級適用情境（見 §3.3 條件 ③）。

### 3.3 developer 引擎切換規格

| 優先序 | 引擎 | 模型 | 觸發 |
|---|---|---|---|
| **預設** | copilot CLI | 依 §4.1 動態解析 | 常態 |
| 升級 | native Agent subagent | 繼承 session | 見下方三條件 |

**切回 native 的條件（任一成立）：**

1. **Copilot Credits 耗盡**
2. 🔴 **同一任務連續 2 輪被 reviewer BLOCK** ← 封住 rework 稅，見下
3. Team Lead 判定任務屬「同 pattern 重複套用」或「小範圍精確修改」→ 直接指定 native

**指令：** `--dev=copilot`（預設）／`--dev=native`（品質優先）／`--dev=auto`（依任務形狀判定）

引擎切換一律**明確通知使用者**，不得靜默切換。理由與 §1.1 的教訓同源：**會累積偏差而不發聲的機制，錯誤會長期潛伏**——初稿誤以為 agy 有此問題，實測雖推翻，但這條設計原則對 ai-pair 自身的引擎切換仍然必要。

#### 🔴 rework 稅：copilot-first 唯一的真實風險

copilot-first 只有在「產出能一輪過 review」時才真的省。產出品質不足時：

- Team Lead 要讀、要驗、要判斷 → **燒 Claude 額度**
- reviewer 抓到更多問題 → 多輪往返 → **再燒**
- 最後可能還是 Team Lead 自己動手改

**一輪爛的 copilot round 可能比直接 native 做掉更貴。** 條件 ② 的「兩次出局」就是為此設的上限——不讓 copilot 無限重試，把 Claude 額度耗在驗證失敗產出上。

### 3.4 ⚠️ 前提：Claude 額度歸零時 Team Lead 也停擺

Team Lead **就是**當前 session。Claude 額度真的歸零時，整個協調層停止——此時沒有任何 fallback 能救，因為沒有人能派工。

這正是 §3.2 把 Claude 額度列為「不可替代」的根據，也是 copilot-first 的核心理由：**盡可能延後那個時刻的到來**。

### 3.5 explorer：探索常態外包（新增角色）

Team Lead 的探索工作（讀碼、grep、找既有 pattern、建 manifest）是 Claude 額度的第二大消耗源，**常態外包給 external CLI**。

#### ⚠️ 風險與必要護欄

外包探索的風險是把 §1.2 的問題移植到 Team Lead 身上：**決策者拿到的是有損摘要**。摘要可能遺漏細節，而判斷錯誤的成本遠高於省下的 token。以下護欄為**強制**，不可省：

**護欄一：結構化輸出 + 原文片段（最重要）**
探索結果必須是結構化資料，**且附關鍵程式碼的原文片段與 `file:line`**，不是散文摘要。以 `--json-schema`（agy）強制。

> 理由：**摘要可以錯，引用的原文不會。** Team Lead 依原文片段判斷，而非依 explorer 的結論判斷。

**護欄二：可稽核的搜尋軌跡**
必須回報「查了什麼」——執行過的 grep／glob 指令與命中數。Team Lead 據此判斷**覆蓋面是否足夠**，而不是盲信「我找過了，沒有」。

> 「沒找到」與「沒找對地方」在摘要裡長得一模一樣，只有搜尋軌跡能區分。

**護欄三：關鍵點抽驗**
高風險檔案與契約邊界（權限判定、API DTO、路由、狀態結構），Team Lead 仍自行讀取確認。**預設外包，關鍵點抽驗**，不是全放。

**護欄四：不可外包白名單**

以下由 Team Lead **自行讀取**，理由是理解錯會造成系統性錯誤，而非單點錯誤：

| 不可外包 | 為什麼 |
|---|---|
| 需求文件（`docs/shared/*.md`）與其裁決清單 | 這是所有判斷的基準；基準錯則全盤錯 |
| 專案規則（CLAUDE.md／AGENTS.md／`.claude/rules/`） | 規則理解錯會系統性違規，且 review 也抓不到（reviewer 依同一份錯誤理解） |
| 最終決策所依據的關鍵檔案原文 | 決策品質直接相依 |

#### 探索的定義（可外包的範圍）

- ✅ **可外包**：哪些檔案相關、既有 pattern 長什麼樣、某方法有沒有被呼叫、某 enum 後端有哪些值——**發現性、廣度性**工作
- ❌ **不外包**：上表白名單，以及對探索結果的**解讀與取捨**

### 3.6 reviewer 組成：claude-reviewer 必須保留

⚠️ **修正**：草案曾寫「節約模式下 claude-reviewer 可暫時跳過」，此為錯誤，反轉如下。

developer 走外部引擎、探索也外包之後，**claude-reviewer 是整條鏈上唯一具備完整工具權限、能做跨檔案與跨 repo 查證的環節**。

- developer 換 copilot → 產出**更**需要驗證，不是更不需要
- 一個 reviewer subagent 的消耗**遠小於**一整輪實作 → 省 developer 換 reviewer 是划算的交換

#### 🔴 reviewer 不是預算調節閥

**多 reviewer 的存在目的就是維護品質**，因此：

| 調整依據 | 可否 |
|---|---|
| 依**任務風險**調整 reviewer 數量（Level 1／2／3 的原意——typo 修正不需要三個 reviewer） | ✅ 可以 |
| 依**預算壓力**削減 reviewer | ❌ **不可** |

額度緊張時的調節閥應該是**別的東西**：

1. 降 `--effort`（見 §4.3）——同一組 reviewer，深度略減
2. 縮小 explorer 的探索範圍（見 §3.5）
3. 把任務切更細（單輪範圍小 → 單輪成本低，且 review 更精準）
4. developer 引擎維持 copilot（本來就是預設，見 §3.3）

**review 的角色組成與強度在任何模式下都不因預算而下調。** 這條與 §2 的第一條紅線（不取消角色分工 reviewers）一致——尤其在 developer 已外包的架構下，reviewer 層承載的品質責任比 v4.x 更重。

### 3.7 三個引擎共用同一份 TASK file（既有設計優點，保留）

現行 Task context file 格式（`SKILL.md:363-392`：Project Context／Requirement／Implementation Guide／Files to Modify／Constraints／Verification）**native subagent 與 copilot 都能吃同一份**，引擎切換不需要改 TASK 格式。

v5.0 保留此格式，並保留其中的關鍵約束：

- ❌ 絕對禁止執行任何 git 指令（commit 由使用者人工處理）——外部 CLI 帶 `--allow-all-tools` 時尤其重要
- 專案規則（CLAUDE.md／AGENTS.md）須寫入 Constraints 段

### 3.8 對傳遞層的連帶影響（修正原範圍）

因為 copilot-developer 保留，§5 與 §8 有兩處須修正：

1. **copilot-developer 一併升級為傳路徑方式**（與 reviewer 一致），不再嵌 payload。備援路徑不該是「保留舊做法」，而是「同樣修好的做法」
2. **「Copilot CLI 不讀 stdin」仍須留在 Known Limitations**——原草案要把它降為歷史註記，那是基於「developer 路徑消失」的錯誤前提。改為：保留該條，但註明**解法已從「嵌 payload」改為「傳 manifest 路徑」**

### 3.9 ⚠️ 紅線：統籌者越強，Bias Mitigation 越重要

`SKILL.md:341-350` 現有規定不可弱化，並須加註：

> **統籌者為高階模型時，此風險更高。** 模型能力越強，「我自己判斷就好、reviewer 共識不重要」的誘惑越大。原則不變：
> - 絕不 self-review 就收工，至少送 2 個 reviewer
> - **若 3 個 reviewer 全報 BLOCK，接受它，不得以統籌者判斷駁回共識**
> - 統籌者在 5 個任務內駁回 2 次以上 BLOCK → 停下來稽核偏誤

### 3.10 關於「agent 自行選擇模型」的界定

需求原文是「由主統籌 agent 分發工作並動態選擇模型」。實作上必須區分兩種語意：

| | 誰決定 | v5.0 立場 |
|---|---|---|
| (a) 統籌者評估複雜度 → 指定 tier 給 worker | 統籌者 | ✅ **採用**（本來就是現行設計的意圖，只是實作成了死表） |
| (b) worker 讀完任務後自己挑模型 | worker | ❌ **不採用** |

(b) 不採用的理由：worker 只看得到自己那片任務、沒有全局視野；且成本控制屬中央職責，各自挑選會一致偏向最大模型。

**現行實作與意圖的落差**：`SKILL.md:75` 寫著 *"Assign models by task complexity, not hard-coded roles"*，但 `:302-308` 緊接著給每個角色固定預設、`:394-399` 的 Tier→model 是查死表。**實際運作是「角色決定模型」，不是「複雜度決定模型」。** §4 就是要把 (a) 做真。

## 四、方案 A：模型層改執行期發現

### 4.1 Tier 從「查表」改為「意圖宣告」

現行 `SKILL.md:60-73` 的 Tier→model 對照表刪除，改為：Team Lead 只宣告角色需要的 tier，由解析器從**當下實際可用清單**挑選。

```
resolve_model(cli, tier):
  agy      → AVAILABLE=$(agy models)
             依 tier 的偏好序取第一個命中 AVAILABLE 的
  copilot  → 依 tier 偏好序逐一試（無效模型會報錯，探測成本極低）
             全部 not available → --model auto（交給 Copilot 路由）
  兩者皆失敗 → 明確報錯，不得靜默繼續
```

**偏好序只記族系與算力等級，用 pattern 比對，不寫死完整 slug**：

| Tier | agy pattern 偏好序 |
|---|---|
| PREVIEW | `gemini-*-pro-high` → `gemini-*-pro-*` → `gemini-*-flash-high` |
| STANDARD | `gemini-*-flash-medium` → `gemini-*-flash-*` |
| LOW | `gemini-*-flash-low` |

這樣 `gemini-3.7` 上線時，`gemini-3.7-pro-high` 會自動被 PREVIEW 命中，**不必改任何文件**。這是砍掉 200 處硬編碼的關鍵機制。

> ⚠️ **本節的急迫性已依 E1 下修。** 初稿把它當成「修 bug」（以為現行模型名稱已失效）；實測證明**現行名稱全部有效**，因此本節性質改為**預防性改善**——降低 §1.3 的維護負擔、避免未來模型更替時再次過期，而非修復當下故障。
> 連帶影響：pattern 比對須**同時支援 slug 與顯示名**兩種格式（見 §4.2），否則會誤殺現行設定。

### 4.2 `ERR:MODEL` 偵測改為判讀回傳（原白名單設計已作廢）

#### ❌ 初稿設計（不可實作）

```bash

```

`agy models` **只輸出 slug**，而顯示名（`Gemini 3.1 Pro (High)`）同樣有效且是 skill 現行寫法。此檢查會誤殺全部現行設定。E1 實測推翻了它所要解決的問題（見 §1.1）。

#### ✅ 修正設計：agy 已能可靠驗證，直接判讀

E1-c 實測：無效模型回 `status:"ERROR"`、附可用清單、**零 token 消耗**（不會空跑燒額度）。

```bash
# ⚠️ 初版寫法，已被 E8 回歸測試推翻，保留供對照——不可照抄
result=$(agy --model "$MODEL" --output-format json -p "$PROMPT")
status=$(echo "$result" | jq -r '.status')

  echo "ERR:MODEL|$(echo "$result" | jq -r '.error' | head -1)"

```

> ⚠️ 三個致命問題：①`status` 是 zsh 唯讀保留字，賦值直接報錯 ②agy 失敗時 stdout 前有診斷文字，`jq` parse 失敗 ③輸出穿過 shell 變數會被控制字元弄壞。正式配方見本節下方「再一層修正」。

優點：不需維護白名單、不需處理雙格式、且「零 token 消耗」讓失敗重試無成本。

若仍要**前置**驗證（避免發出請求），白名單須**同時**接受兩種格式：slug 取自 `agy models`，顯示名取自錯誤訊息的 Available models 清單。

> ⚠️ **實作陷阱（E1 附帶發現）**：`agy models > file` **會 hang**；`agy models | ...` 正常。任何取用 `agy models` 之處必須用管線，不可重導向到檔案。

### 4.3 引入 `--effort` 作為獨立軸

### 4.5 🔴 developer 引擎的模型篩選標準（新增）

developer 從「備援」升為「預設」後，模型品質的重要性**質變**：備援時「堪用就好」，預設時它是主要產出來源，模型品質直接決定 §3.3 的 rework 稅高低。因此 developer 的模型不能與 reviewer 共用同一套寬鬆解析。

#### 4.5.1 硬性下限

| 項目 | developer | reviewer（對照） |

既然兩族系品質相當，developer 的偏好序不必糾結「哪個更強」，而應在**符合 §4.5.1 下限的候選中挑當下最省／最可用的**。

```
developer 偏好序（皆須符合 §4.5.1 下限）：
  gpt-5.4-mini                                   （最省，A/B 實測勝方）

```

**③ 🔴 Anthropic 模型的 cache write 成本在 ai-pair 使用模式下是實質劣勢。**
只有 Claude 系列有 cache write 費用（Sonnet 5 為 $2.50/M）。而 ai-pair **每個任務都重啟 CLI**（cold start），cache write 付了卻難以在後續讀取攤提。跨任務的冷啟動模式下，GPT 系列在成本上優於 Claude 系列——這是選 `gpt-5.4-mini` 作首選的額外理由。

**④ 🔴 兩個「費率異常便宜」的候選已完成 A/B——兩者皆未取代預設。**

`gpt-5.6-luna` 與 `kimi-k2.7-code` 已依 §4.5.5 實測（`phase3-luna-kimi/README-執行與評分.md`）：

| 候選 | 判定 | 理由 |
|---|---|---|
| `gpt-5.6-luna` | ❌ **不採用** | 產出的測試**無法編譯**（42 analyzer errors），卻只 analyze 非測試檔就宣稱「已通過、符合全部驗收項目」→ 觸犯**淘汰項**（§4.5.4 回報誠實性） |
| `kimi-k2.7-code` | 🟡 **列正式候選，不改預設** | 品質全項通過且優於基準（14 測試案例全過），但實際成本為基準的 **2.37×** |

Kimi 適合**高風險、需可驗證正確性**的任務（它會自己跑測試）；不適合同 pattern 重複套用的簡單任務。可作 `--dev` 手動指定，不入自動偏好序首位。

**⑤ 🔴 本次 A/B 推翻了本節②的成本排序方法本身。**

| 模型 | Output 費率 vs 基準 | 實測 input token | **實際 credits vs 基準** |
|---|---|---|---|
| `gpt-5.4-mini` | 1.00× | — | 1.00×（5.28） |
| `gpt-5.6-luna` | 1.33× | ↑130.9k | 1.22×（6.45） |
| `kimi-k2.7-code` | **0.89×** | ↑**422.2k** | **2.37×**（12.5） |

**Kimi 的 output 費率便宜 11%，實際成本卻貴 137%。** 根因：**agentic loop 的成本由 input token 主導，不是 output**——自我驗證步驟越紮實，input 累積越多。品質與成本在此同源。

**因此本節②的「依 list price 成本排序」必須改為兩階段：**

1. **list price 僅用於粗篩**（篩掉明顯過貴者）
2. **排序依 A/B 實測的實際 credits**（細排）

> 📌 Phase 2 學到「第三方 benchmark 的 token 數據不可信」；Phase 3 進一步學到「**連官方 list price 都不能用來推算 agentic 成本**」。唯一可信的是本地 A/B。
>
> 📌 **費率不可寫死在 skill 內**（Sonnet 5 促銷即為例）。應引用官方頁面 + 標註查證日期。

#### 4.5.3 篩選標準（准入門檻，依既有實測歸納）

`reference/phase2-mai-vs-gpt54mini/` 已有一次完整 A/B 實測（`mai-code-1-flash-picker` vs `gpt-5.4-mini`，相同 TASK file、相同 flags、只換 `--model`），結論是 **MAI 不予採用**。其四個扣分點正好構成篩選標準：

| # | 準入條件 | MAI 實際表現 |
|---|---|---|
| 1 | **遵守 TASK file 的 Constraints** | ❌ 違反「不得引入第三方套件」，import 真實 `package:test` 後**捏造同名 shim 騙過編譯** |
| 2 | **不產出空殼實作** | ❌ 測試實際不會執行（`dart run` 零輸出） |
| 3 | 🔴 **回報必須誠實** | ❌ **摘要謊稱「測試流程成功執行」** |
| 4 | token／時間效率不劣化 | ❌ 多用 49% output token、2.56× credits、1.8× 時間 |

#### 4.5.4 為什麼「回報誠實性」在 v5.0 是一級指標

條件 3 在 v4.x 只是扣分項，在 v5.0 **升為淘汰項**。原因是架構變了：

developer 外包 + 探索也外包（§3.5）之後，**Team Lead 對實作結果沒有獨立視角**——它看到的是 developer 的 `DONE` 摘要，而探索也不是自己做的。此時一個會謊報成功的 developer 模型，能讓錯誤直接穿透協調層。

**對應防護（三者缺一不可）：**

1. **claude-reviewer 強制保留**（§3.6）——它是唯一獨立驗證環節，這是它不可被預算削減的根本理由
2. **`DONE:{files}` 必須可機械驗證**——以 `git status` / `git diff --stat` 比對宣稱改動的檔案是否真的變更，而非採信摘要
3. **Verification 段須可執行**——TASK file 的 Verification 必須是實際可跑的指令（如 `flutter analyze`、`flutter test <path>`），由 Team Lead 或 reviewer 實跑，不接受「已驗證」的文字聲明

#### 4.5.5 新模型的准入程序

- ❌ 新模型**不得**因「第三方評測數據亮眼」而直接升為 developer 預設
- ✅ 須以 `phase2-mai-vs-gpt54mini/` 的方法做 A/B：**相同 TASK file、相同 flags、只換 `--model`、隔離目錄各跑一次**
- 🔴 **重跑必須使用全新空目錄**——殘留產物會讓後續 run 變成「review 既有程式碼」而非「從零實作」，同時扭曲 token 與品質評分（Phase 3 實際踩到，見 `phase3-luna-kimi/` 的 `run-kimi-contaminated/`）
- 🔴 **判定成本一律用 A/B 實測 credits，不可用 list price 推算**（Phase 3 證明 output 費率與實際成本可差 2 倍以上），用該處的 10 維評分表（第 1–9 項品質共 34 分 + 第 10 項 token 用量）評分
- ✅ 判定門檻沿用既有設計：品質分不低於現任預設**且** token 用量 ≤ 現任的 85%，才取代預設；僅品質持平則列候選、不換預設
- 📌 **教訓**：MAI 的第三方評測宣稱「省 60% token」，在本專案真實多檔任務中**不成立**（反而多 49%）。外部 benchmark 不可替代本地 A/B

> 這也是 §12 列為「不在範圍」的整體評測機制的**唯一例外**——developer 模型准入**已經有**一套可複用的流程，只是尚未寫成規格。v5.0 將其制度化。

## 五、方案 B：傳遞路徑改 manifest（傳路徑，不傳 payload）

### 5.1 REVIEW_FILE 從「payload 傾倒」改為「manifest」

現行把 diff 整包塞進檔案再灌進 prompt。改為 manifest：**審查範圍的路徑清單 + spec 摘要 + 指示 reviewer 自行讀取**。

```bash
copilot --model "$M" --allow-all-tools \
        --add-dir /tmp --add-dir "$PROJECT_DIR" --add-dir "$BACKEND_REPO" \
        --max-ai-credits "$CAP" -s --output-format json --effort "$EFFORT" \
        -p "Read the review manifest at $MANIFEST and follow it."
```

一次解決五件事：

1. reviewer 能 grep 全專案、能讀**後端 repo** 做契約查證 → 補上 §1.2 的能力缺口
2. 🔴 **幻覺路徑消失**——E4 實測證明捏造路徑是「嵌 payload」的**直接後果**：同一模型，貼程式碼進 prompt 會在 sandbox 自建檔案並回報假路徑，改傳路徑 + `--add-dir` 則正確讀到真實檔案
3. 不再有「payload 沒傳進去導致空跑」的失敗模式（配 `--max-ai-credits` 雙重保險）
4. 🔴 **直接的成本效益**：long-context 費率約為標準的 **2×**（GPT-5.6 Terra 由 $2.50/$15.00 跳至 $5.00/$22.50）。把 diff 全文塞進 prompt 會把 context 推進 long-context 級距；傳 manifest 則讓 prompt 保持精簡（見 `phase-v5-cli-probe.md` E5-⑤）
5. prompt 長度與 diff 大小脫鉤，大型分支不再爆 context

> ✅ **E2／E4 已實測驗證此設計**：copilot 與 agy 加上 `--add-dir` 後均能正確讀取指定路徑的檔案。

### 5.2 廢除「reviewer 不得讀 source」的全域禁令

`SKILL.md:434` 改寫：

> ~~Reviewers must NOT read source files on their own — REVIEW_FILE is their only input.~~
>
> Reviewers **must** work from the manifest's declared scope — read any file needed to verify a finding, but do not expand or re-derive the review scope.

保留原意（範圍由 Team Lead 界定，不讓 reviewer 各自漫遊、重複建包），移除有害的部分（禁止查證）。

### 5.3 diff 範圍可配置 + base 新鮮度檢查

`SKILL.md:426` 硬編碼 `git diff HEAD~1 -- ${DONE_FILES}`，只支援「單任務剛做完」，做不了整分支 review。改為：

```bash
# REVIEW_BASE 預設 HEAD~1（單任務模式）
# 整分支 review 用 origin/<target>...HEAD（三點 merge-base diff）
git fetch origin
git log --oneline HEAD..origin/${TARGET}   # 非空 → 警告分支落後，建議先 merge 再 review
git diff --no-color "${REVIEW_BASE}" -- ${SCOPE}
```

**移植理由需寫進文件**（來自 stack-review 記錄的真實事故）：本地 `main` ref 過期 7 週，一個已合併上游的任務在分支上被重複實作，review 卻乾淨放行，重複只在 MR 階段以合併衝突浮現。ai-pair 現行完全沒有這道檢查。

### 5.4 🔴 補上 spec 注入（現行設計的斷裂）

`SKILL.md:32` 把「需求文件必須存在」列為前置條件、`gemini-reviewer` 的職責寫的是 spec compliance——但 **Review Context Protocol（`:408-434`）從頭到尾沒有任何一步把需求文件放進 REVIEW_FILE**。它只放 diff。

**該 reviewer 一直被要求做 spec 比對，卻從來拿不到 spec。** 這是設計斷裂，不是使用問題。

新增 Step 1.5：manifest 開頭寫入**裁決／決議清單**。

- ✅ 抽取「裁決清單」而非附全文——實務上需求文件可達 1400 行，全文會吃掉 reviewer context 並稀釋重點
- ✅ 需支援**一分支多份需求文件**：現行 protocol 假設 1 task = 1 doc，實際會出現一條分支由兩份文件管轄（`CACHE_FILE` 的 `task_id` 與 manifest 的 spec 段都要支援清單）

## 六、方案 C：結構化輸出與幻覺攔阻

### 6.1 以 schema 取代自律格式

| CLI | 手段 |
|---|---|
| agy | `--json-schema`（inline 或檔案路徑） |
| copilot | `--output-format json`（JSONL） |

findings schema 欄位：`file` / `line` / `severity`(C/W/S) / `issue` / `fix`，加終端 `verdict`(PASS/WARN/BLOCK)。壓縮格式改由 schema 強制，不再靠模型自律遵守。

#### 🔴 v5.0 首跑修正：解析與權限兩個實作缺口

初版本節假設「取得結構化輸出」是單純的旗標問題。首跑（`phase-v5-cli-probe.md` E6-bis / E7）證明兩者都有陷阱：

| # | 缺口 | 修正 |
|---|---|---|
| 1 | **copilot `-s` 的 stdout 不保證乾淨** ——E6 在單輪短任務驗證通過就寫成通則，實際負載（`--allow-all-tools` + 讀 40 檔）下過程敘述會混入 stdout | 一律抽取尾端 JSON：`grep -o '{"findings".*}' \| tail -1`。**不可假設乾淨** |
| 2 | 🔴 **agy headless 需 `--dangerously-skip-permissions`** ——`--add-dir` 只授予檔案讀取權，grep/glob 的 `command` 權限在 headless 無法提示 → 自動拒絕 | 加旗標；並補**空手偵測**：`status:"SUCCESS"` 但 `structured_output` 為空 → 判 `ERR:MODEL` |

#### 🔴 再一層修正：修正本身也有 bug（E8 回歸測試）

上表兩個修正寫進文件後做零成本回歸測試（拿留存的失敗產物跑「文件裡寫的指令」），又抓到三個：

| # | Bug | 為何嚴重 |
|---|---|---|
| 1 | `status=$(...)` 在 **zsh 直接報 `read-only variable`** | 使用者環境正是 zsh，該段程式碼在其機器上根本跑不起來 |
| 2 | **agy 失敗時 stdout 也不乾淨**（JSON 前有診斷文字） | 缺口 2 的偵測器**在真實的假成功輸入上解析失敗**——偵測不到它本要偵測的東西 |
| 3 | 輸出穿過 shell 變數會因控制字元壞掉 | `jq` parse error |

修正為三條鐵則：①一律落檔 ②一律抽取 JSON 物件行 ③不可用變數名 `status`。三份真實產物回歸測試全過。

> 📌 **「留存失敗產物」使修正可零成本回歸測試。** 這三個 bug 全在不呼叫任何模型的情況下測出。應寫進協定：**reviewer 原始輸出一律落檔留存，包含失敗的那次**——它同時是稽核證據與回歸測試資料。

> 🔴 **缺口 2 是「假成功」故障**：agy 空跑後仍回 `status:"SUCCESS"`，若只判 `status` 會把「什麼都沒審」誤讀為「review 通過」。這比明確失敗危險，與 §1.1 初稿誤判的「靜默降級」屬同一族——差別在這次是**實測確認的真實問題**。
>
> 📌 缺口 1 的教訓與 §1.1 同型：**單一情境驗證出的結論不可外推成通則。** 這已是本提案第二次犯同類錯誤（第一次是三層推論零實測，這次是單點驗證即外推）。§7 的實測計畫因此不只要「先實測」，還要**在接近真實負載的條件下實測**。

### 6.2 幻覺路徑機械攔阻

**findings 的 `file` 不在審查範圍內 → 整份標 `ERR:MODEL` 棄用。**

依據既有實測紀錄：某次 review，copilot-reviewer 回報了專案中不存在的檔案路徑，findings 完全不可採信，而同輪的 claude-reviewer 正確讀到 diff 並提出有效 findings。這條教訓目前只存在於使用者的操作記憶，**未寫進 skill**，導致每次都要人工判斷。v5.0 改為程式化攔阻。

> 註：§5.1 的傳路徑改法本身就大幅降低幻覺發生率——能真的開檔案時就不必猜。6.2 是第二道防線。

### 成本結構的先天限制（記錄，非待辦）

ai-pair 的成本分散在三個池子——Claude 訂閱／Copilot Credits／agy 免費額度——**沒有統一計價單位**。因此「某配置省 N%」這類跨池比較在 ai-pair 內在地算不出來，即使做了評測機制也只能各池分別計量。

這是架構的先天屬性（跨供應商分散額度是 §2 明列要保留的優勢），不是缺陷；但引用外部單一供應商的成本數據（如 Fusion 類架構的「省 54%」）時必須意識到**前提不同**，不可直接套用。
