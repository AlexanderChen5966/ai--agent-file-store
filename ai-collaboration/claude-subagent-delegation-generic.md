# Claude Code 分工（Subagent Delegation）設定指南 — 通用版

從本專案（B2B Manager）實戰經驗蒸餾，適用於其他專案導入 Claude Code 多 agent 分工時參考。

**這份文件回答三個問題：**
1. 我的專案**該不該**分工？（§1 決策框架）
2. 分工**怎麼設定**？（§2 三種層級）
3. 分工**需要哪些文件**才不會出事？（§3 文件清單）

> 本專案自身的結論與設定見
> [`claude-subagent-delegation.md`](./claude-subagent-delegation.md)（專案版）。

**最後更新：** 2026-08-14

---

## 0. 三個原則

1. **分工不是預設好處，是一筆有固定成本的交易。**
   subagent 省的是主 session 的 context，不是 token 總量。
2. **分工失敗幾乎都不是 model 能力問題，是文件沒到位。**
   subagent 是全新 context，你沒寫進去的等於不存在。
3. **先手動派工累積數據，再自動化。**
   憑直覺開自動分工，等於讓 AI 用「這看起來很簡單」去決定風險。

## 1. 決策框架：我的專案該不該分工

分工的期望值由**兩個維度**決定，不是由專案「有多先進」決定。

### 維度一：規模 —— 主 session 的 context 裝不裝得下？

| 訊號 | 傾向 |
|---|---|
| 單一服務、單一語言、多數任務是既有 pattern 套用 | ❌ 不分工 |
| Monorepo、多服務、跨語言（前端＋後端＋infra） | ✅ 分工 |
| 常有「掃全庫找出所有 X」這類盤點需求 | ✅ 分工（至少用搜尋型 agent） |
| 一次任務要開的檔案通常 < 10 個 | ❌ 不分工 |

### 維度二：規則型態 —— 正面指示 vs 負面約束

這是**比規模更關鍵**、也最常被忽略的維度。

翻開你的 `CLAUDE.md` / `AGENTS.md` / rules，統計兩種句型的比例：

| 型態 | 例句 | 漏掉的後果 |
|---|---|---|
| **正面指示** | 「新頁面放在 `src/pages/`」「用 X 套件做表單」 | 產出**不完整**——一眼看得出來，好修 |
| **負面約束** | 「排序索引**不可**加 1」「**不可**用 disable 呈現」「**不可** upgrade 這個套件」 | 產出**看起來對但錯**——看不出來，上線才爆 |

**負面約束佔比高的專案，分工風險顯著升高。**
因為 subagent 的典型失敗模式是「不知道自己不知道」——它讀了規則文字，
但沒有你踩過那顆雷的記憶，判斷不出當下這個改動正落在禁區裡。

### 四象限結論

```
              負面約束少          負面約束多
            ┌──────────────┬──────────────┐
   規模大   │  ✅ 積極分工   │  ⚠️ 限定分工   │
            │  自動化可行    │  只派安全類型  │
            ├──────────────┼──────────────┤
   規模小   │  🔸 按需分工   │  ❌ 預設不分工 │
            │  盤點類才派    │  主 session 做 │
            └──────────────┴──────────────┘
```

⚠️ **限定分工**與🔸**按需分工**的差別：前者要明確列出禁區清單（見 §4），
後者只在特定情境主動用（搜尋、跨 repo）。

## 2. 三種設定層級

### 層級 A：單次呼叫指定 model（零設定）

```
Agent(subagent_type: "Explore", model: "haiku", prompt: "...")
Agent(subagent_type: "general-purpose", model: "sonnet", prompt: "...")
```

可用 model：`opus` / `sonnet` / `haiku` / `fable`。

⚠️ **`subagent_type: "fork"` 會忽略 `model`**——fork 複製主 session 的完整
context，一律繼承主 session 的 model。要換 model 就別用 fork。

**適合：** 剛開始導入、還在累積數據的階段。建議所有專案從這裡開始。

### 層級 B：agent 定義檔（`.claude/agents/<name>.md`）

```markdown
---
name: <agent-name>
description: <什麼情況該用它——這句話決定它會不會被自動選用>
model: sonnet
tools: Read, Edit, Write, Bash, Grep, Glob
---

（system prompt：必讀文件清單、產出格式、禁止事項）
```

**最重要的欄位是 `description`。**
Claude Code 靠它判斷「這個任務該不該叫這個 agent」。

| ❌ 寫法 | ✅ 寫法 |
|---|---|
| 「這個 agent 會實作前端頁面」（描述能力） | 「當任務有明確需求文件、且屬於既有 pattern 重複套用時使用；不適用於 X / Y 變更」（描述觸發條件與邊界） |

`tools` 欄位是**權限最小化**的手段——不需要寫檔的 agent 就別給 `Write`/`Edit`，
從機制上杜絕它動到不該動的地方。這比在 prompt 裡拜託它別動可靠得多。

### 層級 C：Workflow 腳本編排

多階段、有前後依賴、要平行展開時使用：

```js
await pipeline(tasks,
  t => agent(t.prompt, { model: 'sonnet', effort: 'low' }),      // 實作
  r => agent(`review: ${r}`, { model: 'opus', effort: 'high' })  // 審查
)
```

⚠️ 會一次展開多個 agent、消耗大量 token，**必須使用者明確要求才可啟動**。

**適合：** 大規模遷移、全庫審計、需要對抗式驗證的場景。
不適合日常開發任務。

## 3. 分工需要哪些文件

subagent 看得到的只有下列三類。**這是本文件最該帶走的一節。**

### 3.1 自動載入 —— 不用給，但要確認內容夠用

Claude Code 會自動載入：

| 來源 | 說明 |
|---|---|
| `CLAUDE.md` | 專案根目錄，支援 `@path` import |
| 被 `@import` 的檔案 | 例如 `@AGENTS.md` |
| `.claude/rules/*.md` | 該目錄下所有 `.md` |

⚠️ **成本注意：每個 subagent 都會重新讀一次，不共用主 session 的 prompt cache。**
這是派工的主要固定開銷。規則文件愈肥，分工愈不划算——這也是把規則拆成
「核心自動載入 + 細節 on-demand」的另一個理由。

### 3.2 必須在 prompt 裡明確指名 —— 最容易漏的一類

**凡是被「引用」而非 `@import` 的文件，subagent 都讀不到。**

導入時請自行盤點，做出你專案的對照表：

| 文件類型 | 何時必須指名 | 漏了會怎樣 |
|---|---|---|
| 設計系統 / UI token 文件 | 任何 UI 變更 | 硬編色碼與尺寸，不用既有 token |
| 該次任務的需求 / 規格文件 | 有需求文件的實作任務 | 自行揣測需求，做出規格外的東西 |
| 高風險模組的專屬規則 | 動到該模組時 | 踩已知的雷 |
| API / DTO 契約文件 | 動到介面時 | 欄位對不上另一端 |
| 測試 / 提交慣例 | 要跑測試或提交時 | 格式不合、CI 紅燈 |

> 💡 **快速自檢：** 在 `CLAUDE.md` 搜尋「先讀」「請參考」「詳見」——
> 這些指向的文件如果沒有 `@import`，就全部屬於這一類，派工時必須手動指名。

### 3.3 沒有文件承載 —— 主 session 要自己補進 prompt

這類**完全接觸不到**，包括：

- 本次對話累積的取捨脈絡與決策理由
- 之前試過但失敗、已經否決的方向
- 使用者當下的偏好與優先順序
- 相鄰模組尚未提交的改動
- 存在 memory / 個人筆記裡的經驗

**沒有寫進 prompt 的，等於不存在。**
如果你發現某類經驗一再需要手動補進 prompt——那就是它該被寫成文件的訊號。

## 4. 建立你的禁區清單

派工判準的核心不是「什麼可以派」，而是**「什麼絕對不派」**。

從這幾個來源撈：

1. **既有規則裡所有「不可 / 禁止 / 需明確確認」的條目** —— 直接進禁區
2. **曾經出事、事後補規則的地方** —— 高風險訊號，進禁區
3. **改動範圍看不見的模組** —— 認證流程、路由守衛、狀態管理核心、
   共用元件底層、產生式程式碼的來源檔
4. **改錯不會立刻報錯的地方** —— 這類最危險，因為 subagent 自認成功

反過來，**安全區**的共同特徵：

| 特徵 | 例子 |
|---|---|
| 輸入大、輸出小 | 全庫盤點、找慣例、統計用法 |
| context 可隔離 | 跨 repo 調查、讀外部文件 |
| 明確可平行且互不影響 | 3 個以上獨立的重複樣板 |
| 產出容易驗證 | 有測試覆蓋、有明確驗收條件 |

⚠️ 「3 個以上」是實務門檻：1~2 個獨立任務直接做通常更快，
**平行省的是時間不是 token**。

## 5. 派工 prompt 模板（必備四段）

```
【任務】
（一句話講清楚要做什麼，含範圍邊界：改哪些檔、不要動哪些檔）

【必讀文件】
1. <設計系統 / token 文件路徑>
2. <本次需求文件路徑>
3. <相關模組的專屬規則路徑>

【禁止事項】
- <從 §4 禁區清單抄相關條目>
- 超出上述範圍的檔案不要動，遇到就回報而非自行決定

【回報格式】
只回報：改了哪些檔、每檔做了什麼（各一行）、遇到的疑問。
不要把檔案內容貼回來。
```

**四段各自防一種失敗：**

| 段落 | 防什麼 |
|---|---|
| 任務 | 範圍蔓延 |
| 必讀文件 | 不知道規則存在（§3.2） |
| 禁止事項 | 不知道自己踩雷（§1 維度二） |
| 回報格式 | **成本失控**——subagent 回貼檔案內容會直接吃掉分工省下的開銷 |

## 6. 成本模型

```
派工成本 = subagent 冷讀規則文件（無 cache）
         + subagent 讀 prompt 指名的文件
         + subagent 實際工作
         + 主 session 讀回報
         + 主 session 驗證產出
         + （做錯時）重派一輪

直接做   = 規則已在 context 且 cache 命中
         + 實際工作
```

**只有當「省下的 context 佔用」大於上述固定開銷時才划算。**

常見誤解：

| 誤解 | 實際 |
|---|---|
| 「Sonnet 比 Opus 便宜，派工省錢」 | 冷讀規則 + 驗證 + 重做的開銷常大於價差 |
| 「平行派工省 token」 | 平行省的是**時間**，token 反而增加 |
| 「小任務派給小 model 剛好」 | 小任務的固定開銷佔比最高，最不划算 |
| 「subagent 也讀得到 CLAUDE.md，所以規則都在」 | 只有自動載入那部分在；引用型文件與對話脈絡都不在 |

## 7. 導入步驟

1. **跑一次 §1 決策框架**，確定你在哪個象限
2. **盤點 §3.2**（搜尋「先讀 / 詳見 / 請參考」），做出必讀文件對照表
3. **建立 §4 禁區清單**，寫進 `CLAUDE.md`
4. **用層級 A 手動派工 3~5 次**，只派安全區任務，記錄 §8 的指標
5. 確認某類任務穩定成功後，才把它固化成 `.claude/agents/` 定義檔（層級 B）
6. **要開自動分工**，需在 `CLAUDE.md` 補明確的委派規則區塊，例如：

```markdown
## 任務委派規則
- 跨檔案盤點／找慣例 → Explore（haiku）
- 跨 repo 調查 → general-purpose（sonnet）
- 3 個以上獨立樣板 → sonnet 平行
- <禁區清單各項> → 不委派，主 session 自己做
- 實作完成後 → 呼叫 code-reviewer
```

> 若你的 session 或專案設定裡有「未經要求不得呼叫 Agent 工具」這類限制，
> 它會**完全關閉自動派工**。要開啟自動分工必須先移除該條。

## 8. 驗證方法

用對照實驗取代推論。同一個中型任務做兩次（主 session 直接做 / 派 subagent），比對：

- [ ] **產出正確性** —— 有沒有踩到負面約束（最重要）
- [ ] **實際 token 消耗**
- [ ] **往返輪數** —— 有沒有需要補充說明、重做
- [ ] **主 session context 佔用差異** —— 這才是分工真正買到的東西

累積 3~5 次同類任務的數據，再決定是否寫進委派規則。

**判讀提醒：** 只看「有沒有做完」會高估分工。
subagent 幾乎總是會回報成功——要看的是**做出來的東西對不對**。

## 9. 常見陷阱

| 陷阱 | 說明 |
|---|---|
| **拿 fork 換 model** | `fork` 忽略 `model` 參數，一律繼承主 session |
| **description 寫成能力描述** | 導致該用時不被選、不該用時被選 |
| **給了不需要的 tools** | 唯讀任務給 `Write` 等於自找麻煩；用 `tools` 白名單設硬邊界 |
| **忘了引用型文件不會自動載入** | §3.2 的整類問題，最高頻的失敗原因 |
| **沒限制回報格式** | subagent 回貼大量檔案內容，分工白做 |
| **一次派太多平行 agent** | 驗證成本爆炸，且錯誤模式會同時出現在所有產出裡 |
| **用「看起來簡單」決定派不派** | 簡單與危險無關；要用**禁區清單**判斷，不是用難度 |
| **在規則很肥的專案派小任務** | 冷讀成本固定，任務愈小愈虧 |
