# MAPS 方法論參考指南

## 框架概述

MAPS™ 是一個**人與 AI 協作的落地框架**,用於系統化地構建 AI 能力。

**核心公式**: `MAPS™ = M × A × P × S`

> 注意是「乘法」而非「加法」:任何一項為 0,整體歸零

- **M (Mindset)** - 心智模式: 先升級大腦,再升級模型
- **A (Architecture)** - 架構設計: 好架構,才撐得住規模
- **P (Prompt)** - 提示工程: Prompt 好,模型才會有札氣
- **S (Systems)** - 系統落地: 系統成型,價值恆久

**標語**: "用 MAPS™,讓 AI 從黑箱變藍圖"

## 一、M (Mindset) - 心智模式層

### 核心理念

**從工具思維 → 系統思維 → 資產思維**

```
舊心智: "我知道怎麼做"
├─ 每次重新描述
├─ 經驗無法傳承
└─ 個人能力天花板

新心智: "我把方法封裝成資產"
├─ 一次定義永久復用
├─ 知識可以傳承
└─ 系統能力持續增長
```

### 三個核心轉變

#### 轉變 1: 從臨時方案到系統方案

**舊思維**:
```markdown
問題: 需要整理筆記
方案: 寫一個長 Prompt
結果: 每次重新調整
```

**新思維**:
```markdown
問題: 需要整理筆記
方案: 創建 discussion-organizer Skill
結果: 
├─ 封裝四層判斷邏輯
├─ 團隊共享使用
└─ 持續優化迭代
```

#### 轉變 2: 從追逐工具到構建能力

**舊思維**:
```markdown
看到新工具 → "這個酷" → 學習使用 → 很少用到 → 看下一個
```

**新思維**:
```markdown
遇到需求 → 評估現有能力 → 選擇合適工具 → 整合到工作流 → 形成資產
              ↓
        如果沒有合適的 → 構建新能力 → 納入能力庫
```

#### 轉變 3: 從個人經驗到組織資產

**舊思維**:
```markdown
個人層面:
- 我知道怎麼用 ChatGPT
- 我會寫 Prompt
- 我有一些技巧

問題:
- 離職後經驗消失
- 新人需要重新摸索
- 無法規模化
```

**新思維**:
```markdown
資產化層面:
- Skills 庫: 封裝判斷邏輯
- Agent 庫: 定義工作流程
- Prompt 庫: 標準化表達
- 知識庫: 記錄最佳實踐

優勢:
- 可傳承、可複用
- 新人快速上手
- 持續優化積累
```

### 心智培養練習

#### 練習 1: 隱性知識顯性化

```markdown
步驟:
1. 選擇一個你經常做的任務
2. 寫下你是怎麼做的(步驟)
3. 寫下你為什麼這麼做(判斷依據)
4. 識別哪些是隱性知識

範例:
任務: 審核文章
步驟: 讀一遍 → 找問題 → 修改

隱性知識挖掘:
- 什麼叫"問題"? → 語法錯誤/邏輯漏洞/表達不清
- 怎麼判斷"嚴重性"? → 影響理解程度
- 優先處理順序? → 先邏輯後文采

結果: 把隱性知識轉為可傳授的規則
```

#### 練習 2: 評估任務的資產化價值

```markdown
評估框架:

任務: [填寫具體任務]

□ 重複頻率: 每週 ___ 次
□ 單次耗時: ___ 分鐘/小時
□ 需要專業判斷: 是 / 否
□ 有標準化流程: 是 / 否
□ 依賴隱性知識: 是 / 否

計算:
資產化價值 = 頻率 × 耗時 × 判斷複雜度

決策:
> 50 分: 🔥 高優先級,立即資產化
20-50 分: ✅ 中優先級,計劃資產化
< 20 分: ⏸️ 低優先級,暫不處理
```

### 心智層的常見陷阱

#### 陷阱 1: 工具收集癖

**症狀**:
```markdown
- 每週都在試新工具
- 收藏夾裡幾十個 AI 工具
- 很少深度使用任何一個
- 總覺得"還有更好的"
```

**解決方案**:
```markdown
限制原則:
1. 同類工具最多保留 2 個
2. 新工具必須解決現有痛點
3. 一個月不用就刪除
4. 專注深度而非廣度
```

#### 陷阱 2: 完美主義

**症狀**:
```markdown
- 一直在規劃,遲遲不動手
- 擔心方案不夠完美
- 過度設計初期架構
- 因為細節糾結而放棄
```

**解決方案**:
```markdown
MVP 原則:
1. 先做能用的最小版本 (1 小時內)
2. 實際使用 3-5 次
3. 基於反饋迭代
4. 完美是迭代出來的,不是設計出來的
```

#### 陷阱 3: 個人英雄主義

**症狀**:
```markdown
- "我自己做比教別人快"
- 不願意分享經驗和資源
- 擔心被替代而保留技巧
- 團隊無法共享能力
```

**解決方案**:
```markdown
資產化思維:
1. 你的價值不是「會做」,而是「能建系統」
2. 分享經驗 = 放大影響力
3. 團隊能力提升 = 你的領導力體現
4. 資產化後,你專注更高價值的工作
```

## 二、A (Architecture) - 架構設計層

### 核心理念

**從單點能力 → 模塊化設計 → 可擴展系統**

```
架構三原則:
1. 單一職責: 每個模塊只做一件事
2. 接口清晰: 輸入輸出明確定義
3. 可組合性: 模塊可以靈活組合
```

### 架構分層模型

```
L4: 生態集成層
├─ 跨平台協作 (Claude + Make + MCP)
├─ 企業級部署
└─ API 聚合

L3: 系統編排層  
├─ 軟編排 (Skill 調度 Subagent)
├─ 硬編排 (Make/N8N workflow)
└─ 條件分支與異常處理

L2: 能力組合層
├─ Skill 調用 Skill
├─ Skill + MCP 工具
└─ 多 Agent 協作

L1: 單一能力層
├─ 獨立 Skill (封裝判斷邏輯)
├─ 獨立 Subagent (專職任務)
└─ 單一工具調用
```

### 架構優化原則

#### 原則 1: 最小權限

```markdown
不要給過多的工具權限

❌ 錯誤:
allowed-tools: [*]  # 允許所有工具

✅ 正確:
allowed-tools: [file_operations, task]  # 僅必需工具

原因:
- 減少安全風險
- 避免意外調用
- 提高執行效率
```

#### 原則 2: 單一職責

```markdown
每個 Skill/Agent 只做一件事

❌ 錯誤:
Skill: universal-helper
功能: 翻譯 + 摘要 + 格式化 + 數據分析

✅ 正確:
Skill: translator (專注翻譯)
Skill: summarizer (專注摘要)
Skill: formatter (專注格式化)
Skill: analyzer (專注分析)

原因:
- 易於測試和調試
- 便於復用和組合
- 降低維護複雜度
```

#### 原則 3: 接口清晰

```markdown
明確定義輸入輸出

❌ 錯誤:
輸入: "一些文本"
輸出: "處理結果"

✅ 正確:
輸入:
- 格式: Markdown 文件
- 大小: < 50KB
- 編碼: UTF-8
- 必需字段: [標題, 內容]

輸出:
- 格式: JSON
- 結構: {title, summary, keywords[]}
- 字段說明: [詳細描述]

原因:
- 減少歧義和錯誤
- 便於自動化測試
- 易於對接其他模塊
```

#### 原則 4: 失敗優雅

```markdown
設計失敗處理機制

基本策略:
1. 輸入驗證: 開始前檢查
2. 中間檢查點: 關鍵步驟後驗證
3. 錯誤記錄: 寫入日誌文件
4. 回滾機制: 失敗後恢復狀態
5. 友好提示: 告訴用戶問題和建議

示例:
```python
# 階段 0 開始前
if not validate_input(input_file):
    log_error("輸入格式錯誤")
    return error_message

# 階段 1 完成後
if not verify_output("stage-1-output.json"):
    log_error("階段 1 輸出異常")
    rollback_to_stage_0()
    return retry_or_abort
```
```

## 三、P (Prompt) - 提示工程層

### 核心理念

**清晰表達是人機協作的基礎**

```
好 Prompt 的三層結構:

L1: 意圖層 (What)
└─ 告訴 AI 要做什麼

L2: 約束層 (How)
└─ 告訴 AI 怎麼做

L3: 規範層 (Quality)
└─ 告訴 AI 做到什麼程度
```

#### 技巧 2: 使用結構化格式

```markdown
## 為什麼要用結構化?

人類看到:

- 摘要多長?

❌ 模糊描述:

✅ 結構化要求:

  "keywords": ["string", "max 5 items"],
  "category": "enum [tech, business, lifestyle]",
  "confidence": "float (0.0-1.0)"
}
```

## 好處
- 輸出格式統一
- 易於程序處理
- 減少歧義
- 便於驗證
```

- 未觸發場景: 用戶說"幫我處理字幕"
- 當前觸發詞: "字幕轉文章"
- 問題: 觸發詞覆蓋不足

**假設**: 增加觸發詞可提升準確率

**實驗**: 
- 添加: "處理字幕", "字幕整理", "subtitle"
- A/B 測試: 50% 用戶用新版本

**結果**:
- 新版本觸發準確率: 85%
- 無誤觸發增加
- 決定: 全量發布新版本

## 常見問題

### Q1: MAPS 和其他方法論的區別?

**A**: MAPS 專注於「人與 AI 協作」這個特定場景。不同於傳統軟件工程方法論,MAPS 強調:
- 資產化思維 (M)
- 模塊化設計 (A)
- 自然語言工程 (P)
- 快速迭代 (S)

### Q2: 必須全部用上 M/A/P/S 嗎?

**A**: 是的。MAPS 是乘法關係,缺任何一項都會大打折扣:
- 缺 M: 做不成資產,只是臨時方案
- 缺 A: 無法規模化,維護困難
- 缺 P: 人機協作低效
- 缺 S: 無法落地,停留在想法階段

### Q3: MAPS 適用於哪些場景?

**A**: 凡是需要「重複使用 AI 能力」的場景都適用:
- ✅ 個人: 工作流自動化、知識管理
- ✅ 團隊: 標準化流程、能力共享
- ✅ 企業: AI 能力平台、規模化應用

不適用:
- ❌ 一次性任務
- ❌ 高度創意性工作
- ❌ 不需要復用的場景

### Q4: 如何評估 MAPS 的效果?

**A**: 三個維度:
1. **效率**: 時間節省、成本降低
2. **質量**: 輸出一致性、錯誤率
3. **資產**: 可復用次數、團隊共享程度

### Q5: MAPS 和 TBRC 的關係?

**A**: 
- **MAPS**: 方法論框架,解決「如何做事」
- **TBRC**: 內容框架,解決「如何組織知識」
- **關係**: TBRC 是 MAPS 在內容組織層面的具體應用

APPLY   → 規模化,團隊共享
