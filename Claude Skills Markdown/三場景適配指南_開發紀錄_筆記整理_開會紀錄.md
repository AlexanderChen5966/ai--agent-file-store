# 三大場景適配指南：Obsidian 知識庫 × MAPS 資產化

---

## 場景一：軟體開發紀錄、問題追蹤、技術文件整理

### 為什麼特別適合

軟體開發的痛點是「經驗散落在各處」——Bug 修過但沒記錄、架構決策的理由忘了、同樣的問題三個月後又踩一次。這些全是高價值的隱性知識，正好適合用 TBRC 框架結構化，再用 Skill 自動整理。

### Vault 結構建議

```
Dev-Vault/
├── 00 Inbox/                    # 丟入未整理的內容
├── 01 Projects/                 # 進行中的專案
│   ├── project-alpha/
│   └── project-beta/
├── 02 Issues/                   # 問題紀錄（核心資產）
│   ├── resolved/                # 已解決
│   └── open/                    # 進行中
├── 03 Architecture/             # 架構決策紀錄（ADR）
├── 04 Runbooks/                 # SOP / 操作手冊
├── 05 TIL/                      # Today I Learned 短筆記
├── 06 References/               # API 文件、第三方套件筆記
├── 07 Archive/                  # 完結專案
└── Templates/
    ├── issue-template.md
    ├── adr-template.md
    └── til-template.md
```

### 筆記模板

#### Issue / Bug 紀錄模板

```yaml
---
title: 
date: {{date}}
tags: [bug, {{project}}, {{technology}}]
type: issue
status: [open/investigating/resolved]
severity: [critical/high/medium/low]
environment: [production/staging/local]
related: []
resolution_time: 
---

## 問題描述
（一句話描述現象）

## 重現步驟
1. 
2. 
3. 

## 根因分析
（為什麼會發生）

## 解決方案
（怎麼修的，含關鍵程式碼片段）

## 預防措施
（怎麼避免再次發生）

## 相關資源
- [[相關 Issue]]
- 參考連結
```

#### ADR（架構決策紀錄）模板

```yaml
---
title: "ADR-{{number}}: {{decision_title}}"
date: {{date}}
tags: [adr, {{project}}, {{domain}}]
type: adr
status: [proposed/accepted/deprecated/superseded]
superseded_by: 
---

## 情境（S）
（當時的技術背景和限制條件）

## 問題（C → Q）
（遇到什麼衝突，核心要回答什麼問題）

## 決策（A）
（選了什麼方案）

## 考慮過的替代方案
| 方案 | 優點 | 缺點 | 不選的原因 |
|------|------|------|-----------|
| A    |      |      |           |
| B    |      |      |           |

## 後果
（這個決策帶來了什麼影響，正面和負面都記）
```

### TBRC 應用方式

以一個 Bug 紀錄為例：

- **T（核心論點）**：這個 Bug 的根因是什麼，本質上是哪一類問題（race condition / config drift / dependency conflict...）
- **B（邊界）**：影響哪些環境、哪些版本、重現條件是什麼
- **R（實踐路徑）**：修復步驟、驗證方法、部署流程
- **C（總結）**：學到什麼、需要加什麼防護措施、相關的其他 Issue

### Skill 設計：`dev-knowledge-organizer`

```
觸發條件：當使用者將技術筆記丟入 Inbox
執行邏輯：
1. 判斷類型（Bug / ADR / TIL / Reference）
2. 根據類型套用對應模板
3. 自動提取 tag（程式語言、框架、錯誤類型）
4. 搜尋 Vault 中是否有相似的歷史 Issue，建立 [[wikilink]]
5. 更新對應的 MOC 索引
6. 移動到正確的資料夾
```

### 實際效益

- 三個月後再遇到類似問題，搜尋 tag 就能找到完整的根因分析和修復方案
- 新成員加入時，直接瀏覽 Issues/resolved 和 ADR 資料夾就能理解歷史脈絡
- 架構決策有紀錄，避免「當初為什麼這樣做」的反覆爭論

## 場景二：個人雜亂筆記整理、分類、紀錄

### 為什麼特別適合

這是 Karpathy 原始用法的直接映射。你的筆記可能來自各種來源——網頁文章、Podcast 心得、靈感片段、學習紀錄——格式不統一、分類混亂、存了找不到。這正是讓 AI 代替你整理的最佳場景。

### Vault 結構建議

```
Personal-Vault/
├── 00 Inbox/                    # 所有東西先丟這裡
├── 01 Projects/                 # 有明確目標和期限的事
│   ├── side-project-X/
│   └── learning-plan-Y/
├── 02 Areas/                    # 持續關注但沒有截止日的領域
│   ├── career/
│   ├── health/
│   ├── finance/
│   └── skills/
├── 03 Resources/                # 主題式參考資料
│   ├── AI/
│   ├── programming/
│   ├── productivity/
│   └── reading-notes/
├── 04 Archive/                  # 完成或不再活躍的內容
├── 05 MOC/                      # Map of Content 索引頁
└── Templates/
    ├── fleeting-note.md         # 閃念筆記
    ├── literature-note.md       # 閱讀筆記
    ├── permanent-note.md        # 永久筆記
    └── weekly-review.md         # 每週回顧
```

### 筆記模板

#### 閃念筆記（快速捕捉）

```yaml
---
title: 
date: {{date}}
tags: []
type: fleeting
status: inbox
source: [thought/article/conversation/podcast]
---

（直接寫，不用管格式，後續 AI 會處理）
```

#### 閱讀筆記（文章/書籍）

```yaml
---
title: "讀書筆記：{{book_or_article_title}}"
date: {{date}}
tags: []
type: literature
status: inbox
source: {{url_or_book_name}}
author: 
rating: [1-5]
---

## 一句話總結
（這篇在說什麼）

## 三個關鍵收穫
1. 
2. 
3. 

## 我的想法
（和我現有知識有什麼關聯、哪裡認同/不認同）

## 可行動的點
（讀完之後我可以做什麼）
```

### TBRC 應用方式

對每一篇經過整理的筆記：

- **T（核心論點）**：這篇筆記的核心洞察是什麼？用一句話總結
- **B（邊界）**：這個洞察在什麼情境下成立？什麼時候不適用？
- **R（實踐路徑）**：如果要用這個洞察，具體怎麼做？
- **C（總結）**：和 Vault 中哪些筆記有關？下一步行動是什麼？

### Skill 設計：`note-processor`

```
觸發條件：當使用者說「整理 Inbox」或「處理新筆記」
執行邏輯：
1. 掃描 00 Inbox/ 中的所有 .md 檔案
2. 對每篇進行判斷：
   ├─ 類型判斷：fleeting / literature / permanent / reference
   ├─ 價值判斷：⭐1-5 重要性評分
   ├─ 主題判斷：屬於哪個 Area 或 Resource
   └─ 連結判斷：和 Vault 中哪些筆記相關
3. 補充 frontmatter 的缺失欄位
4. 生成一句話摘要寫入筆記頂部
5. 建立 [[wikilink]] 連結
6. 移動到對應資料夾
7. 更新相關 MOC 索引頁
8. 輸出本次處理報告：
   「本次處理 X 篇筆記，N 篇移至 Resources，M 篇移至 Areas，
    建立了 Y 個新連結，發現 Z 篇可能重複的內容。」
```

## 場景三：開會紀錄

### 為什麼適合（但需要調整）

開會紀錄的特點是「格式高度標準化、但內容每次不同」。它不需要複雜的多層判斷，但需要快速提取 action items、追蹤待辦、和專案筆記連結。這更適合用「模板 + 輕量 Skill」的方式處理，而不是完整的 TBRC 四層。

### Vault 結構建議

在你的主 Vault 中新增：

```
├── Meetings/
│   ├── 2026/
│   │   ├── 05/
│   │   │   ├── 2026-05-13-週會.md
│   │   │   └── 2026-05-14-需求討論.md
│   │   └── ...
│   ├── recurring/              # 定期會議的 MOC
│   │   ├── weekly-standup.md
│   │   └── sprint-review.md
│   └── action-items.md         # 所有待辦的匯總頁
```

### 筆記模板

#### 會議紀錄模板

```yaml
---
title: "{{date}}-{{meeting_name}}"
date: {{date}}
tags: [meeting, {{project}}, {{team}}]
type: meeting
meeting_type: [standup/review/planning/1on1/ad-hoc]
attendees: []
status: [draft/reviewed/closed]
related_project: [[]]
---

## 會議目的
（一句話：這次會開來做什麼）

## 討論要點
### 議題 1：{{topic}}
- 討論內容摘要
- 結論：

### 議題 2：{{topic}}
- 討論內容摘要
- 結論：

## Action Items
- [ ] {{who}} - {{what}} - 截止：{{deadline}} #action
- [ ] {{who}} - {{what}} - 截止：{{deadline}} #action

## 決策紀錄
| 決策項目 | 決定 | 原因 | 負責人 |
|---------|------|------|--------|
|         |      |      |        |

## 下次會議
- 日期：
- 需要準備：
```

### Skill 設計：`meeting-processor`

```
觸發條件：當使用者貼入會議逐字稿或原始筆記
執行邏輯：
1. 從原始內容中提取：
   ├─ 參與者名單
   ├─ 討論的議題（自動分段）
   ├─ 每個議題的結論
   ├─ 所有 action items（含負責人和截止日）
   └─ 做出的決策
2. 套用會議紀錄模板格式化
3. 將 action items 同步到 action-items.md 匯總頁
4. 如果議題和現有專案相關，建立 [[wikilink]]
5. 存入 Meetings/{{year}}/{{month}}/ 資料夾
```

### 搭配 SCQA 的用法

開會紀錄不太需要 TBRC 的完整四層，但 SCQA 很適合用在會議中的「決策議題」：

- **S**：目前的狀況是什麼（數據、進度）
- **C**：遇到什麼阻礙或變化
- **Q**：這次會議要決定什麼
- **A**：決定了什麼，下一步怎麼做

這讓會議紀錄不只是「誰說了什麼」，而是有清晰的決策脈絡。

### 進階：Action Items 自動追蹤

在 Obsidian 中用 Dataview 插件，可以自動匯總所有會議中的未完成 action items：

```dataview
TASK FROM "Meetings"
WHERE !completed AND contains(tags, "action")
SORT date DESC
```

這樣你打開 `action-items.md` 就能看到所有待辦，不用翻每一份會議紀錄。

## 三場景整合：一個 Vault 搞定全部

如果你希望三個場景共用一個 Vault（推薦做法），結構如下：

```
My-Vault/
├── 00 Inbox/                    # 統一入口
├── 01 Projects/                 # 跨場景共用
├── 02 Dev/                      # 場景一：軟體開發
│   ├── issues/
│   ├── adr/
│   ├── til/
│   └── runbooks/
├── 03 Personal/                 # 場景二：個人筆記
│   ├── areas/
│   ├── resources/
│   └── reading-notes/
├── 04 Meetings/                 # 場景三：開會紀錄
│   ├── 2026/
│   ├── recurring/
│   └── action-items.md
├── 05 MOC/                      # 全域索引
│   ├── dev-index.md
│   ├── personal-index.md
│   └── meetings-index.md
├── 06 Archive/
├── Templates/
│   ├── issue.md
│   ├── adr.md
│   ├── til.md
│   ├── fleeting-note.md
│   ├── literature-note.md
│   ├── meeting.md
│   └── weekly-review.md
└── Skills/                      # 你的 Claude Skills
    ├── dev-knowledge-organizer/
    ├── note-processor/
    └── meeting-processor/
```

### 三個 Skill 的分工

| Skill | 類型 | 觸發方式 | 處理對象 | 輸出 |
|-------|------|---------|---------|------|
| `dev-knowledge-organizer` | 能力包型 | 丟入技術筆記時 | Bug / ADR / TIL | 結構化 Issue，含 wikilink |
| `note-processor` | 能力包型 | 說「整理 Inbox」 | 個人雜亂筆記 | 分類歸檔，含摘要和評分 |
| `meeting-processor` | 能力包型 | 貼入會議逐字稿 | 原始會議內容 | 格式化紀錄，含 action items |

### 建議啟動順序

```
第 1-2 週：先做「個人筆記整理」（note-processor）
           → 最能感受到效果，建立信心和習慣

第 3-4 週：加入「開會紀錄」（meeting-processor）
           → 格式最固定，Skill 最容易寫

第 5-6 週：加入「軟體開發紀錄」（dev-knowledge-organizer）
           → 最有長期複利，但需要磨合判斷邏輯
```

這個順序是根據「見效速度」排的，讓你每兩週都有一個新的 Skill 上線，保持動力。
